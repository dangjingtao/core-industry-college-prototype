
# T06｜核心大使计划共享业务模型与状态

## 目标

先建立 App 与运营后台共用的一套业务真相源，避免两端各自维护团队人数、激活状态和推广成果。

## 范围

建立至少以下业务对象与 mock / prototype 状态：

- `Campaign`：一期核心大使计划；
- `CampaignSchool`：活动覆盖学校及学校招募码；
- `AmbassadorTeam`：核心大使、推广伙伴、团队状态；
- `PromotionSource`：活动 + 团队 + 推广人员；
- `EffectiveAcquisition`：有效新增记录；
- 简单团队激励状态。

固定业务规则：

- 每个团队只有 1 位核心大使；
- 同一期活动中，一个用户只能属于一个推广团队；
- 1 位核心大使 + 至少 3 位推广伙伴后团队自动激活；
- 4 人只是激活门槛，不是人数上限；
- 活动期间不可退队、不可换队；
- 活动结束后团队关系结束，但历史记录保留。

## 不做

- 不做永久大使等级；
- 不做多级代理 / 子团队；
- 不做真实财务结算系统；
- 不在本卡锁定真实安装归因技术方案。

## 验收

- [ ] App 与 PC 后台可以读取同一套活动、团队和推广数据；
- [ ] 团队人数从 3 人变为 4 人时，状态自动从「组建中」变为「推广中」；
- [ ] 活动结束后团队与二维码进入失效状态，但历史数据仍可读取；
- [ ] 不出现 App 与后台对同一团队状态各说各话的第二真相源。

# T07｜App：核心大使申请、组队与激活

## 目标

完成学生从学校招募码进入，到成为核心大使、组建团队并点亮身份的完整 App 链路。

## 范围

### 核心大使申请

- 学校招募码入口；
- 未登录用户先登录 / 注册，再回到申请流程；
- 大使申请表；
- 条款勾选；
- 提交后直接获得「核心大使 · 待点亮」；
- 生成并展示「团队招募码」。

### 推广伙伴加入

- 新用户可注册后加入；
- 已注册但未绑定本期其它团队的老用户可直接加入；
- 已绑定其它团队时明确阻止重复加入；
- 加入成功后显示所属团队与推广伙伴身份；
- 不提供退队、换队入口。

### 团队激活

- 大使页展示组队进度；
- 总人数达到 4 人时自动激活；
- 大使身份由「待点亮」变为「已点亮」；
- 激活后仍允许继续招募更多推广伙伴。

## 页面控制

首版尽量控制在：

1. 大使申请页；
2. 核心大使页；
3. 推广伙伴活动状态页。

不要为了每个状态复制一套页面。

## 验收

- [ ] 学校招募码 → 登录 / 注册 → 申请 → 待点亮链路可完整走通；
- [ ] 大使可以通过团队招募码连续加入 3 名推广伙伴；
- [ ] 第 3 名推广伙伴加入后团队自动激活；
- [ ] 激活后继续加入第 4、5 名推广伙伴不受阻；
- [ ] 已绑定其它团队的用户无法重复加入；
- [ ] App 中不存在主动退队或换队入口。

## 依赖

T06。

# T08｜App：专属推广码与团队推广成果

## 目标

完成团队激活后的推广阶段，并严格落实核心大使与推广伙伴的数据权限差异。

## 范围

### 专属推广码

团队激活后：

- 核心大使获得自己的专属推广码；
- 每名推广伙伴获得自己的专属推广码；
- 后续新加入已激活团队的推广伙伴也立即获得专属推广码；
- 未激活团队不开放正式推广码。

原型中需要能够模拟：

```text
专属推广码
→ 下载 / 注册链路
→ 新用户注册成功
→ 记录活动 + 团队 + 推广人员
→ 形成 1 个有效新增
```

只验证业务归因结果，不要求本卡实现真实 App Store / Android 安装归因服务。

### 核心大使权限

新增「团队推广成果」入口，至少展示：

- 团队人数；
- 团队有效新增总数；
- 每名团队人员对应的有效新增数量；
- 简单推广明细占位 / mock。

### 推广伙伴权限

推广伙伴只能看到：

- 所属团队；
- 活动状态；
- 自己的专属推广码。

不得看到：

- 自己的有效新增数量；
- 团队总有效新增；
- 其它成员数据；
- 排行榜。

## 验收

- [ ] 未激活团队没有可用专属推广码；
- [ ] 激活后全员都有独立推广码；
- [ ] 模拟一个新用户注册后，只给对应推广人员增加 1 个有效新增；
- [ ] 已注册用户不重复计为有效新增；
- [ ] 核心大使能看到团队成果；
- [ ] 推广伙伴完全看不到个人及团队成果数字。

## 依赖

T06、T07。

---

# T09｜运营后台：活动、学校、团队与激励

## 目标

完成运营方从创建一期活动，到查看学校、大使团队、推广成果和激励状态的后台工作流。

## 范围

后台首版保持三层：

```text
活动列表
→ 活动详情
→ 团队详情
```

### 活动列表

展示：

- 活动名称；
- 时间；
- 状态；
- 覆盖学校数；
- 核心大使数；
- 已激活团队数；
- 有效新增总数。

### 创建 / 编辑活动

支持：

- 活动名称；
- 开始 / 结束时间；
- 参与学校；
- 大使申请字段；
- 活动条款。

激活门槛首版固定为 `1 位核心大使 + 3 位推广伙伴`，不做复杂规则配置器。

### 学校招募码

- 每所学校生成独立的大使招募二维码；
- 二维码关联活动 + 学校；
- 支持查看 / 下载二维码；
- 可查看该学校的大使与推广数据。

### 活动详情

顶部展示：

- 覆盖学校；
- 核心大使数量；
- 已激活团队数量；
- 推广伙伴数量；
- 有效新增总数。

下方团队列表至少包含：

- 核心大使；
- 学校；
- 团队状态；
- 团队人数；
- 有效新增；
- 激励状态。

### 团队详情

展示：

- 大使申请信息；
- 学校；
- 团队状态；
- 团队人数；
- 成员列表；
- 每人有效新增；
- 团队总有效新增；
- 必要推广明细；
- 简单激励状态：未处理 / 已处理。

## 不做

- 不拆独立代理中心、结算中心、数据中心；
- 不计算团队内部个人分成；
- 不给推广伙伴逐人结算；
- 不重做现有 PC 报名门户，与其保持边界清楚。

## 验收

- [ ] 可以创建一项活动并配置多所学校；
- [ ] 每所学校都有独立招募码；
- [ ] App 产生的大使、团队人数与有效新增能在后台正确看到；
- [ ] 可从活动列表进入活动详情，再进入团队详情；
- [ ] 后台可查看成员级推广成果；
- [ ] 激励状态可记录，但不出现个人分账功能。

## 依赖

T06。可与 T07 并行。

# T10｜前后台联动、生命周期与最终验收

## 目标

把 T06–T09 串成一个完整的可交互业务原型，并验证前后台状态、权限和生命周期一致。

## 必验场景

### 场景 A｜大使组队激活

```text
后台创建活动 + 学校招募码
→ 学生扫码申请核心大使
→ App 显示待点亮
→ 后台出现该大使团队
→ 3 名推广伙伴加入
→ 团队自动激活
→ App 大使已点亮
→ 后台团队状态=推广中
```

### 场景 B｜团队继续扩张

```text
团队已激活
→ 大使继续邀请新推广伙伴
→ 新成员加入
→ 团队人数继续增加
→ 新成员立即获得专属推广码
```

### 场景 C｜有效新增归因

```text
某推广伙伴专属推广码
→ 新用户注册成功
→ 对应人员 +1 有效新增
→ 大使端团队成果同步变化
→ 后台活动 / 团队数据同步变化
→ 推广伙伴本人仍看不到成果数字
```

### 场景 D｜活动结束

```text
后台活动结束
→ 团队自动结束
→ 招募码失效
→ 专属推广码失效
→ 不再产生新增推广成果
→ 历史团队 / 推广成果仍可查看
→ 用户可在后续新活动重新参加
```

## 工程验收

- [ ] App 与 PC 均可正常 build；
- [ ] 新路由不存在明显死链 / 空入口；
- [ ] App 与后台对活动、团队、有效新增使用同一业务真相源；
- [ ] 权限符合 PRD：大使可看团队成果，推广伙伴不可看；
- [ ] 活动结束后二维码与团队关系状态正确收口；
- [ ] 不破坏现有参赛、就业 / 实习等母动线；
- [ ] 最终补最小必要的浏览器 / E2E 证据，不以“页面画完”代替业务验收。

## 依赖

T06、T07、T08、T09 全部完成。

---

## 本轮完成定义

T06–T10 全部通过后，应可以向产品 / 运营现场演示一条完整链路：

> **运营建活动并发学校招募码 → 学生成为核心大使 → 拉 3 名伙伴点亮团队 → 全员推广 → 核心大使看团队成果 → 运营后台看全局与团队结果 → 活动结束自动收口。**

如果这条链路不能完整走通，即使单独页面已经完成，也不能判定「核心大使计划」完成。
