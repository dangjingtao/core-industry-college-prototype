# 08｜三创赛报名端职责与团队生命周期设计

> 状态：Current Design / T029 施工依据  
> 日期：2026-08-24  
> 关联：T028、T029、F00、T025、GAP-05、PC02  
> 上位账号设计：`06-account-lifecycle-and-phone-binding.md`、`07-account-activation-and-identity-confirmation.md`

---

## 1. 本轮已确认产品结论

### 1.1 报名主端：PC

当前三创赛报名采用：

```text
PC 响应式报名门户 = 主报名端
Mobile App = 赛事发现 / 登录 / 状态回流 / 无电脑场景兜底入口
```

Owner 已确认队长在 PC 登录 / 注册并完成团队报名，因此本次会议中“整个报名流程全面迁移手机端”的表述不再作为当前施工方案。

手机端继续保留 F00 已完成的 handoff：

```text
App 赛事详情
→ 打开同一套响应式报名门户
→ 完成报名 / 查看状态
→ callback 回 App
```

手机端不再新造一套原生长表单，不产生第二份 Registration truth source。

### 1.2 队长负责团队报名

- 队长使用核心学院长期账号在 PC 登录 / 注册；
- 队长创建团队，团队 ID 系统生成且只读；
- 队长直接录入团队成员赛事资料；
- 队员不需要提前到 PC 单独注册；
- 队员账号创建 / 绑定时点遵守 T028：**学校审核通过后才执行**；
- 已注册成员复用原长期账号，未注册成员创建待激活账号。

### 1.3 审核通过后团队名单锁定

学校审核通过后：

- 不再允许新增成员；
- 不允许用新成员替换旧成员；
- 不允许直接编辑已锁定成员身份事实；
- 后续人员变化只允许走“减员申请”。

### 1.4 减员不上传证明材料

本项目继续沿用 2026-08-19 `GAP-05` 已确认决策：

```text
选择成员
→ 填写原因
→ 提交减员申请
→ 等待审核
```

**不上传减员申请表 / 证明附件。**

本次会议摘要中“需上传减员申请表”与既有确认决策冲突；当前设计以 2026-08-19 明确决策为准，不恢复材料上传。

## 2. PC / Mobile 职责边界

### 2.1 PC 响应式报名门户

负责：

- 队长账号登录 / 注册；
- 赛事规则确认；
- 团队创建；
- 报名期成员录入、修改、删除；
- 团队材料；
- 学校审核状态；
- 审核通过后的项目 / 承诺书等 PC 报名材料流程；
- 报名状态展示与回流。

不负责：

- 赛事期长期团队维护工作台；
- App 长期账号安全；
- 赛事结束后的长期资产管理；
- 另建一套 Mobile Registration Store。

### 2.2 Mobile App

负责：

- 发现赛事；
- 登录长期账号；
- 进入 PC 响应式报名门户；
- 接收报名 / 审核状态 callback；
- 接收审核通过后的账号 / 赛事身份通知；
- 进入赛事工作区；
- 赛事期团队查看；
- 发起减员申请；
- 查看减员审核状态；
- 赛事结束后的长期经历 / 成绩 / 证书出口。

### 2.3 手机兜底不等于原生重做

无电脑用户可以用手机浏览器 / WebView 打开同一响应式报名门户。

产品表达应明确：

> 复杂报名推荐电脑完成；手机仍可继续，但不会为手机单独维护第二套报名数据和页面规则。

## 3. 团队生命周期

推荐状态：

```text
Draft
  ↓ 队长提交
SchoolReviewPending
  ├─ rejected → Draft/Edit
  └─ approved
       ↓
ApprovedLocked
       ↓
OfficialPending / Ready（按赛事接入方式）
       ↓
InProgress
       ↓
Ended
```

### 3.1 Draft

允许：

- 修改团队名称 / 联系信息；
- 添加成员；
- 删除成员；
- 修改成员赛事报名资料；
- 保存草稿。

不发生：

- 普通队员账号创建；
- 赛事身份绑定；
- 长期账号资产写入。

### 3.2 SchoolReviewPending

团队报名事实冻结等待学校审核。

- 不允许继续改成员；
- 不创建普通队员长期账号；
- 不绑定正式赛事身份；
- 审核驳回后回到可编辑状态；
- 审核通过后进入 `ApprovedLocked`。

### 3.3 ApprovedLocked

学校审核通过后的关键动作：

1. 团队名单锁定；
2. 触发 T028 Account Resolution；
3. 未注册成员创建待激活账号；
4. 已注册成员关联本次赛事身份；
5. 写短信 / 站内通知；
6. 后续不允许增员或替换。

账号处理失败的个别成员进入人工补偿，**不能因此把团队重新解锁**。

---

## 4. 学校审核与官方赛事确认不能混成一个状态

现有产品基线已经明确三层事实：

```text
外部权威赛事事实
平台承接报名流程
核心学院叠加服务
```

因此三创赛需要区分：

```text
SchoolReviewStatus
OfficialQualificationStatus
CompetitionIdentityStatus
```

### 4.1 学校审核通过

表示：

- 校内报名真实性 / 基础资格通过；
- 团队名单进入锁定状态；
- 可以触发 T028 账号创建 / 绑定；
- 可以继续允许 PC 端后续项目材料流程（按赛事规则）。

它**不必天然等于**“外部三创赛官方资格已最终确认”。

### 4.2 外部官方确认

对于需要外部权威确认的赛事：

```text
school approved
→ official pending
→ official confirmed / rejected
```

只有官方确认与赛事生命周期条件都满足后，才开放正式赛事 Workspace 权限。

对于平台直接承接、没有第二层外部权威确认的普通赛事，可由赛事配置声明：

```text
school approval = final qualification
```

不能把这个简化规则写死为全平台规则。

## 5. TeamMembership 与 CompetitionIdentity

长期账号、团队关系、赛事身份必须分开：

```text
UserAccount
  └─ userId

TeamMembership
  ├─ competitionId
  ├─ teamId
  ├─ userId / registrationMemberId
  ├─ role
  └─ status

CompetitionIdentity
  ├─ competitionId
  ├─ userId
  ├─ identityStatus
  └─ acknowledgementStatus
```

团队锁定后手机号即使未来换绑，也不能生成新的团队成员事实。关系应最终落到稳定 `userId` / `CompetitionIdentity`，而不是永久绑死在旧手机号上。

## 6. 减员状态机

### 6.1 可提交阶段

现有 `GAP-05` 语义是“赛事期团队维护”。

因此当前原型继续：

- 报名编辑期：直接编辑名单，不叫减员申请；
- 学校审核中：成员冻结，不允许变更；
- 审核通过名单锁定后：后续人员变化类型只能是减员；
- 实际减员入口默认在赛事工作区中按赛事配置开放；
- 赛事结束后关闭新减员申请。

这里区分两个概念：

> “审核后只允许减员”是**允许的变更类型**；  
> “什么时候开放减员入口”是**赛事配置 / 生命周期规则**。

当前三创赛原型仍在 `inProgress` 开放减员，不把开放时点写死为“审核通过立即开放”。

### 6.2 请求状态

```text
none
→ pending
→ approved | rejected | cancelled
```

`pending` 时：

- 当前 TeamMembership 不变；
- 当前成员列表不变；
- 赛事权限不变；
- UI 明确“审核前不会直接改成员事实”。

`approved` 后：

```text
TeamMembership: active → removed
CompetitionIdentity: active → revoked / removed（仅本赛事）
UserAccount: 保持 active
LongTermAssets: 保持
```

`rejected` 后不改变任何团队事实。

## 7. 减员申请字段

当前最低字段：

- competitionId；
- teamId；
- memberId / userId；
- 原成员显示信息；
- reason；
- applicantUserId；
- submittedAt；
- reviewStatus；
- reviewer / reviewedAt（审核后）。

不需要：

- 上传减员申请表；
- 上传证明材料。

### 7.1 队长减员是特殊状态

如果被减员者是当前队长，不能直接提交普通减员。

推荐流程：

```text
选择当前队长
→ 先从现有剩余成员中指定新队长
→ 再提交减员申请
```

这不是“替换队员”，只是团队内现有成员角色交接。

如果赛事规则不允许队长变更，则直接阻止并提示联系赛事运营。

### 7.2 最低人数 / 赛事规则校验

减员不能把通用平台逻辑写死成某个固定人数。

提交前按赛事配置校验：

- 最低团队人数；
- 受保护角色；
- 是否允许队长变更；
- 当前阶段是否允许减员。

规则不满足时不提交，而不是先删成员再等待后台发现问题。

### 7.3 同一时间只允许一个待审核减员请求

首期建议一个团队同一时刻只允许一笔 `pending` 减员请求，避免多个请求并发修改同一成员真相。

通过 / 驳回 / 撤销后再允许下一笔。

## 8. 关键异常状态

### A. 学校审核驳回

```text
SchoolReviewPending → rejected → Draft/Edit
```

- 队长可修正成员；
- 可添加 / 删除；
- 之前没有创建普通队员长期账号，因此不需要“回滚账号”。

### B. 团队审核通过，但某个成员账号创建失败

```text
Team = ApprovedLocked
Member Account Resolution = conflict / failed
```

- 团队仍保持锁定；
- 该成员进入账号人工补偿；
- 不允许队长通过“删除再添加”绕过账号问题。

### C. 未认领账号成员被减员

如果成员在审核通过后已经产生 `provisioned_unclaimed`，但本人尚未激活 App 就被批准减员：

- 不删除整个 UserAccount；
- 本赛事 TeamMembership → removed；
- 本赛事 CompetitionIdentity → revoked / removed；
- 待激活账号是否继续保留，遵守 T028 的无人认领账号保留策略；
- 本人首次登录时不能再显示为当前参赛成员。

### D. 用户点击“这不是我的参赛信息”

T028 `disputed` 属于账号 / 赛事身份归属核验，不自动等价于团队减员。

在核验完成前：

- TeamMembership 事实不自动删除；
- 该账号上的高风险赛事操作暂停；
- 如最终确认手机号录错，再由赛事 / 账号治理流程修正对应关系。

### E. 手机号换绑

审核通过后，团队关系已落到稳定 `userId` / CompetitionIdentity。

用户按 T028 合规换绑手机号后：

- 不新增 TeamMembership；
- 不改变团队角色；
- 不重新报名；
- 不重新生成赛事经历。

## 9. T025 边界

T029 只决定“谁在哪一端完成报名”和“团队生命周期”。

**赛事项目材料是否允许在 App 原生编辑**继续由 T025 决定。

当前不因为 T029 报名主端确定为 PC，就自动得出“所有赛事项目材料永远只能 PC 编辑”的结论；同样也不因为 App 有赛事工作区，就把报名长表单搬进 App。

---

## 10. 原型施工要求

### PC

需要体现：

- 明确标注 PC 是主报名端；
- 报名提交后团队冻结；
- 审核驳回返回编辑；
- 审核通过后名单锁定；
- 审核通过后不显示增员 / 替换入口；
- 减员入口不在报名门户重新造一套表单，而是说明“赛事期在 App 团队页处理”。

### Mobile

需要体现：

- 进入 PC 响应式门户属于兜底 handoff；
- 不出现“手机原生报名表”第二真相源；
- 工作区团队页只提供减员，不提供增员 / 替换；
- pending 时成员列表不变；
- 赛事结束后不能新提交减员。

---

## 11. 暂未拍死的参数

以下不阻塞 T029 主设计：

1. 三创赛具体从哪个阶段开放减员入口；
2. 减员最终由学校老师、平台运营还是分层审核；
3. 队长变更在真实三创赛规则中是否允许；
4. 最低团队人数 / 特殊赛道规则；
5. pending 减员是否允许队长主动撤销。

这些应做赛事配置 / 规则，不应写死进通用账号或团队模型。
