# 05｜PC 管理端产品决策纪要

> 状态：Confirmed Decisions / 可公开  
> 日期：2026-08-18  
> 适用范围：核心产业学院 PC 管理端 `/admin/*` 及其未来后台数据能力  
> 关联文档：[`00-product-master-context.md`](./00-product-master-context.md)、[`03-pc-admin-data-skeleton.md`](./03-pc-admin-data-skeleton.md)

---

## 1. 文档目的

本文记录围绕 PC 管理端进行的一轮产品确认结果。

它不是数据库 Schema，也不是后台页面清单，而是用于回答几个更基础的问题：

- 核心产业学院后台到底是什么；
- 三创赛在系统中处于什么位置；
- 哪些数据由外部权威来源提供，哪些由平台产生；
- 学校、企业、平台运营分别能做什么；
- 赛事、课程、权益、机会、证书等对象如何进入统一管理体系；
- 首期后台必须具备哪些治理能力。

本文中的已确认结论优先用于后续 PC 管理端施工。若与早期探索性描述冲突，以本文的明确决策为准，并在相关文档中逐步同步。

---

## 2. 后台总定位

核心产业学院 PC 后台是**平台控制面**，不是某一赛事的官方后台，也不是学生 App 的桌面版。

核心定位：

> **平台统一管理主体、赛事接入、课程、权益、机会、内容、学生赛事身份、长期可信资产以及运营治理能力，并为 App 提供稳定的数据来源。**

三创赛是当前非常重要的赛事入口和真实业务来源，但不能成为整个后台的信息架构中心。

因此后台应同时支持：

1. **外部权威赛事接入**：以三创赛为当前最重要案例；
2. **平台配置赛事**：企业、合作机构等其它赛事可直接在平台配置；
3. **平台服务叠加**：无论赛事来自哪里，核心产业学院都可以在赛事之上配置自己的课程、权益、创赛工坊、活动等服务。

---

## 3. 三创赛的数据边界

三创赛相关能力必须区分三种不同的数据语义。

### 3.1 外部权威赛事事实

包括但不限于：

- 官方赛事基础信息；
- 统一报名时间；
- 官方规则与阶段窗口；
- 最终官方报名 / 参赛资格状态；
- 其它由权威赛事系统确认的正式事实。

这类数据以外部权威来源为准。

### 3.2 核心产业学院承接的报名流程

核心产业学院可以把三创赛报名作为重要入口，并承接部分报名交互与流程，例如：

- 学生进入报名；
- 队长 / 队员信息；
- 团队资料；
- 学校真实性审核；
- 报名过程状态；
- 与 App 的状态回流。

但必须保持：

```text
平台报名流程状态 ≠ 官方最终参赛资格状态
```

平台流程完成或学校审核通过，不等于已经取得官方参赛资格。

### 3.3 核心产业学院叠加服务

平台可以在三创赛事实层之上提供自己的服务，例如：

- 三创赛专属课程；
- 赛事权益；
- 创赛工坊；
- 活动；
- 资料与运营服务。

这些属于核心产业学院的平台能力，不应描述成三创赛官方提供的服务。

---

## 4. 三创赛数据接入策略

### 4.1 API 优先

外部权威赛事数据原则上优先通过 API 自动同步。

### 4.2 文件导入作为兜底

后台同时保留：

- Excel / 文件导入；
- 人工校对；
- 必要的人工修正。

用于 API 暂不可用、数据缺失或应急运营。

### 4.3 数据来源必须可追踪

后台至少需要区分：

```text
API 同步
文件导入
人工修正
```

每条关键数据应能追溯来源。

### 4.4 冲突处理

当官方 API 与人工数据发生冲突时：

- 官方 API 默认作为权威来源；
- 人工修正只能作为明确的临时覆盖；
- 人工覆盖必须填写原因并留下操作记录；
- 后续同步发现冲突时必须显式提示，不能静默覆盖或吞掉差异。

---

## 5. 报名入口是赛事级能力

报名方式不能写死为“三创赛报名”。

每场赛事应能够配置自己的报名接入方式，例如：

- 核心产业学院自有 / 承接的报名门户；
- 外部报名页面；
- API / 第三方报名系统；
- 暂无线上报名。

三创赛是当前最重要、接入最深的案例，但底层仍使用通用赛事报名接入模型。

### 官方确认与赛事工作区

对于需要外部权威确认参赛资格的赛事：

> **在官方资格确认回来之前，学生不能进入正式赛事工作区。**

平台可以展示报名处理状态，但不能用平台内部 `approved` 替代正式参赛资格。

---

## 6. 地方赛节点与时间管理

需要区分官方统一时间与地方执行时间。

### 官方统一时间

例如统一报名时间，由赛事官方确定，平台负责同步或展示，不由学校自行修改。

### 地方执行节点

校赛、省赛等具体时间可能由地方在官方窗口内自行确定。

后台默认采用：

> **平台运营代录为主，成熟地区可授权地方人员自维护。**

具体授权范围后续按真实合作模式细化，但底层数据模型需要支持“官方窗口 + 地方节点”的分层结构。

---

## 7. 赛事项目不是长期 Project

已明确采用赛事期项目模型：

```text
Competition
  └─ CompetitionProject
```

项目属于具体赛事上下文，不作为一个跨赛事长期维护的 Project 主数据。

赛事结束后长期保留的是：

- 项目摘要；
- 参赛经历；
- 团队角色；
- 比赛成绩；
- 证书；
- 其它可信空间。

后台不建设重型、跨赛事的长期项目管理系统。

---

## 8. 学校审核模型

### 8.1 团队审核责任

跨校团队由**队长所在学校**统一审核整个团队。

例如：

```text
A 校队长
+ B 校队员
→ A 校授权老师负责该团队审核
```

不要求多个学校分别完成成员审核后再合并团队状态。

### 8.2 学校老师的数据访问范围

学校老师只能看到与**当前授权赛事 + 当前授权学校**直接相关的数据，例如：

- 报名资料；
- 团队与成员；
- 参赛项目材料；
- 必要联系方式；
- 审核状态；
- 被授权处理的赛事变更事项。

默认不得访问：

- 学生其它赛事；
- 长期问卷 / 画像；
- 求职简历；
- 投递记录；
- 权益消费记录；
- 创赛工坊中的具体个人回答 / AI 内容；
- 与当前审核无关的长期账号数据。

### 8.3 学校内容共建

学校可以提供本校活动 / 权益内容，但首期不直接拥有发布权。

方向为：

```text
学校提交
→ 核心产业学院运营审核
→ 平台发布
```

考虑首期交付规模，这部分不列为最优先能力。

---

## 9. Organization 统一主体主数据

学校、企业、赛事组织方、合作机构等统一使用 `Organization` 作为后台主体主数据。

通过类型、关系和权限区分主体，而不是分别建设互不关联的企业表、学校表、机构表。

典型结构：

```text
Organization
├─ School
├─ Company
├─ Competition Organizer
└─ Partner / Resource Provider
```

赛事、课程、权益、活动、机会、内容等对象都通过稳定 `organizationId` 与主体建立关系。

该后台 `Organization` 概念不等价于学生 App 历史 D08“主体管理”。

---

## 10. 企业后台策略

首期不建设完整企业自运营后台。

采用：

> **默认由核心产业学院运营代录；后续根据合作成熟度逐步开放企业自维护。**

未来企业自维护时，只能操作自身 Organization 范围内被授权的资源，不获得平台级管理权限。

---

## 11. 课程是平台托管能力

课程全部由核心产业学院平台托管，不把“外部学习链接”作为正式课程的主要形态。

PC 后台直接管理：

- 课程；
- 章节；
- 视频；
- 小测试；
- 完成条件；
- 赛事关系；
- 权益关系；
- 证书规则。

### 11.1 首期课程完成模型

首期不建设万能学习规则引擎。

主要形态收敛为：

```text
视频学习进度
+ 小测试通过
→ Course Completed
```

后台只需要配置必要的学习完成要求和测试及格条件。

### 11.2 赛事课程

所有课程都可以配置为某场赛事的专属课程，例如赛事入门课程。

课程任务按**个人**完成，不按团队共享完成状态。

“必修”不默认强制阻断赛事主流程。课程完成状态可以被其它平台规则引用，例如：

- 是否可领取某项权益；
- 是否满足证书条件；
- 是否可使用某项平台服务。

避免把课程规则直接等同于官方赛事资格规则。

---

## 12. 可信证书与签发流程

核心产业学院不冒充外部权威签发主体，但平台具备对接**真实外部权威签发渠道**并主动发起签发流程的业务能力。

后台需要如实记录：

- 证书类型；
- 实际签发主体；
- 签发编号；
- 签发状态；
- 文件 / 凭证；
- 验真入口或验真信息；
- 申请与回流记录。

### 12.1 课程证书

课程是确定的可信证书签发场景。

流程为：

```text
运营预先配置证书规则
→ 学生满足课程完成条件
→ 系统自动触发签发流程
→ 外部签发结果回流
→ 学生长期资产
```

不要求运营逐张人工点击签发。

### 12.2 其它证书

赛事成果、项目实践、活动等场景允许由平台运营根据实际业务发起可信证书签发。

因此证书系统不能写死成“赛事获奖证书”。

---

## 13. 权益管理

权益资格由核心产业学院平台运营统一配置。

首期保持简单，不建设万能权益规则引擎。

### 13.1 个人领取

首期权益按个人领取设计，暂不建设团队权益模型。

### 13.2 首期发放方式

固定支持三类：

1. 兑换码 / 卡密；
2. 外部领取链接；
3. 线下核销 / 人工兑现。

### 13.3 条件引用

权益资格可以引用清晰、可解释的平台事实，例如：

- 是否拥有某赛事身份；
- 是否完成指定课程；
- 是否满足某项公开条件。

---

## 14. 机会与投递边界

核心产业学院提供机会分发、App 内投递和状态跟踪，但不把产品发展成完整招聘平台。

### 14.1 机会来源

PC 后台配置机会，由 App 向学生展示或推送。

岗位详情可以包含：

- 企业官网；
- 企业介绍；
- 第三方参考页面；
- 其它外部信息出口。

但正式投递动作必须在 App 内完成。

### 14.2 Application 真相源

```text
App 内投递
→ 平台 Application
→ PC 运营更新状态
→ App 状态回流
```

首期投递状态由核心产业学院运营统一维护，企业不直接登录后台处理候选人。

### 14.3 定向分发

岗位可以先按规则圈选人群，再由运营确认发送，同时允许人工增删名单。

可以使用的条件包括：

- 学校；
- 专业；
- 赛事经历；
- 课程完成情况；
- 证书；
- 比赛成绩等可信资产。

只能使用明确、可解释的字段，不建立隐藏人才评分或复杂推荐模型。

---

## 15. 内容发布

首页资讯、Banner、赛友内容、活动等，首期统一由核心产业学院运营发布。

学校、企业和合作方可以提供素材，但不直接拥有正式发布权限。

内容需要支持定向范围，首期至少包括：

- 指定赛事；
- 指定学校；
- 指定地区。

暂不建设复杂用户标签和个性化内容推荐系统。

---

## 16. 内部运营权限

PC 后台必须区分：

- 超级管理员；
- 普通运营。

### 16.1 超级管理员

至少负责：

- 后台账号创建 / 停用；
- 权限分配；
- 全局治理；
- 高风险审批 / 执行；
- 必要的异常处置。

### 16.2 普通运营

按：

```text
角色
+ 模块权限
+ 数据范围
```

进行简单授权。

例如可限制到：

- 某几场赛事；
- 企业与资源模块；
- 课程与证书模块；
- 内容与活动模块；
- 某个 Organization 范围。

首期不建设复杂 RBAC 可视化编排系统，但底层权限语义必须保留。

普通运营不能自行创建后台账号或扩大自身权限。

---

## 17. 审计与高风险审批

### 17.1 操作审计日志列为 P0

关键操作必须可追溯：

- 谁操作；
- 什么时候；
- 操作对象；
- 修改前 / 修改后；
- 操作原因；
- 关联审批（如有）。

### 17.2 高风险操作必须审批

普通内容编辑不需要审批，但以下类型需要走“提交 → 审批 → 执行”流程：

- 批量签发 / 撤销证书；
- 人工修正外部权威赛事状态；
- 大批量调整学生赛事身份；
- 扩大运营权限；
- 其它会影响可信事实或大量用户的操作。

审批至少记录：

- 申请人；
- 审批人；
- 申请原因；
- 审批结果；
- 最终执行记录。

---

## 18. 学生账号异常处置

平台需要支持学生账号冻结 / 解冻。

建议治理路径：

```text
普通运营提交异常处置申请
→ 高风险审批
→ 超级管理员 / 授权角色执行
```

冻结只影响账号当前使用权限，不删除：

- 长期资料；
- 赛事历史；
- 成绩；
- 证书；
- 投递记录；
- 其它长期资产。

后台必须区分“限制访问”与“删除历史事实”。

---

## 19. 当前 P0 后台范围

综合以上决策，首期优先级收敛为：

```text
P0
├─ 赛事中心 / 赛事接入
├─ 三创赛 API 与兜底导入
├─ 报名流程与官方资格状态边界
├─ Organization 主体管理
├─ 学生 / 赛事身份 / 学校审核
├─ 平台托管课程
├─ 课程完成与可信证书签发
├─ 权益基础管理
├─ 机会配置 / App 投递状态
├─ 超级管理员 / 普通运营权限
├─ 操作审计
├─ 高风险审批
└─ 学生账号冻结 / 解冻
```

后续再逐步扩展：

```text
P1 / P2
├─ 地方人员自维护赛事节点
├─ 学校活动 / 权益提交
├─ 企业自维护资源
├─ 更完整的线下活动 / 创域运营
└─ 创赛工坊配置与运行观察
```

---

## 20. 后续施工检查原则

PC 后台每增加一个真实管理能力，都应先回答：

1. 这是外部权威事实、平台主数据、平台流程状态，还是长期资产？
2. 权威写入方是谁？
3. 是否存在外部数据源？优先接入方式是什么？
4. 谁能查看？谁能修改？
5. 是否需要模块 / 数据范围权限？
6. 是否属于高风险操作？
7. 是否必须进入审计日志？
8. App 在哪里消费它？
9. 对象结束、下架或账号冻结后，哪些历史事实必须保留？
10. 是否正在无意中把核心产业学院设计成某个单一赛事、招聘平台或其它垂直 SaaS？

最后一条尤其重要：

> **核心产业学院首先是长期服务创新创业学生的平台。三创赛非常重要，但它是平台的重要赛事入口和数据源，而不是整个后台的唯一中心。**
