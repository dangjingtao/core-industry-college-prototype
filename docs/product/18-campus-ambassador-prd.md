# 18｜核心大使计划 PRD

> 状态：Draft / T047 产品规则已同步  
> 日期：2026-08-26  
> 适用：学生 App + 现有 PC 运营管理端  
> 目标：用一套轻量规则完成「招募核心大使 → 组队点亮 → 团队推广 → 查看成果 → 运营激励」闭环。

---

## 1. 需求目标

运营方按一期活动，在学校内招募核心大使并发展推广团队。

首版完成四件事：

1. 运营方创建一期「核心大使计划」，向参与学校提供大使招募二维码；
2. 学生扫码申请成为核心大使，招募推广伙伴，达到 4 人后点亮身份；
3. 团队点亮后，全员使用各自专属推广码带来新用户注册；
4. 核心大使查看本团队推广成果，运营方在 PC 端查看全局数据并处理团队激励。

本功能属于长期账号上的运营活动身份，不属于某一场赛事身份。每期活动结束后团队自动结束，仅保留历史记录。

---

## 2. 角色与统一用词

| 对象 | 产品用词 | 说明 |
| --- | --- | --- |
| 活动 | 核心大使计划 | 按期运行，有开始/结束时间 |
| 团队负责人 | 核心大使 | 每个团队只有 1 位 |
| 大使状态 | 待点亮 / 已点亮 | 身份名称不变化，只变化状态 |
| 普通团队成员 | 推广伙伴 | 不获得大使身份 |
| 大使用于组队的码 | 团队招募码 | 只用于加入推广团队 |
| 全员用于拉新的码 | 专属推广码 | 只用于拉新注册归因 |
| 原“业绩” | 推广成果 | 学生侧统一采用较友好的表达 |
| 成功拉新指标 | 有效新增 | 新用户完成注册后计数 |
| 运营奖励 | 团队激励 | 发给核心大使，平台不处理内部再分配 |

## 3. 整体流程

```text
【PC 运营端】
创建核心大使计划
→ 配置活动时间 / 参与学校
→ 配置大使申请表
→ 选择已发布活动条款版本
→ 每所学校生成大使招募二维码
        ↓
【学生 App】
学生扫码
→ 登录 / 注册
→ 按本期配置填写申请表 + 同意本期条款版本
→ 核心大使 · 待点亮
→ 获得团队招募码
→ 邀请推广伙伴
→ 1 位核心大使 + 至少 3 位推广伙伴
→ 团队点亮
→ 核心大使 · 已点亮
→ 全员获得各自专属推广码
→ 专属推广码 → 下载 App → 新用户注册成功
→ 形成有效新增
        ↓
【学生 App】
核心大使查看团队推广成果
推广伙伴只负责推广，不查看成果数字
        ↓
【PC 运营端】
查看活动 / 学校 / 团队推广成果
→ 处理团队激励
        ↓
活动结束
→ 团队自动结束
→ 招募码 / 推广码失效
→ 保留历史记录
```

## 4. 学生 App 逻辑

### 4.1 核心大使申请

运营方为参与学校提供对应的大使招募二维码。

学生扫码后：

1. 未登录用户先登录或注册，完成后回到申请流程；
2. 按本期活动配置填写大使申请表；
3. 阅读并同意本期活动绑定的已发布条款版本；
4. 提交成功后直接获得「核心大使 · 待点亮」身份，首版不增加人工审核；
5. 系统生成该大使的「团队招募码」。

申请表由 PC 端按活动配置。首版支持：

- 单行文本；
- 长文本；
- 单选；
- 多选；
- 字段必填 / 非必填；
- 单选、多选的选项配置。

App 应按活动保存的字段结构渲染，不把「自我介绍、校园传播渠道、参与动机」等固定字段写死为永久产品规则。

用户提交申请时，应同时记录其**实际同意的活动条款版本**，以便后续追溯当期规则。

同一用户在同一期活动中只能属于一个推广团队，不能同时成为其它团队的大使或推广伙伴。

### 4.2 推广伙伴加入

核心大使分享团队招募码。

- 新用户可注册后加入；
- 已注册老用户也可加入；
- 前提是当前未绑定本期其它推广团队；
- 加入后成为「推广伙伴」；
- 活动期间不可主动退队、不可换队。

团队人数无上限，点亮后仍可继续招募。

### 4.3 团队点亮

点亮条件固定为：

> **1 位核心大使 + 至少 3 位推广伙伴，即团队总人数达到 4 人。**

点亮前：

- 核心大使显示「待点亮」；
- 展示组队进度；
- 只开放团队招募；
- 不开放任何人的专属推广码。

点亮后：

- 核心大使显示「已点亮」；
- 团队进入正式推广状态；
- 核心大使和所有推广伙伴获得各自独立的专属推广码；
- 后续新加入已点亮团队的推广伙伴，也获得自己的专属推广码。

### 4.4 专属推广码与有效新增

```text
专属推广码
→ 扫码
→ App 下载流程
→ 安装
→ 新用户完成注册
→ 系统识别推广来源
→ 对应推广人员 +1 有效新增
```

业务口径：

- 从扫码开始必须保留推广来源；
- 每个有效新增能够关联活动、团队和推广人员；
- 仅此前未注册过 App 的新用户注册成功计入有效新增；
- 已注册用户扫码不重复计入；
- 安装归因的具体技术方案由研发确定，本 PRD 不锁定实现方式。

### 4.5 推广成果权限

**核心大使可看：**

- 团队人数；
- 团队有效新增总数；
- 核心大使及各推广伙伴对应的有效新增数量；
- 运营最终确认的必要推广明细。

**推广伙伴可看：**

- 自己已加入的团队；
- 当前活动 / 团队状态；
- 自己的专属推广码。

**推广伙伴不可看：**

- 自己的有效新增数量；
- 其他成员推广成果；
- 团队有效新增总数；
- 排行榜。

### 4.6 活动结束

活动结束后：

- 团队自动结束；
- 团队招募码和专属推广码失效；
- 不再新增推广成果；
- 解除本期团队绑定限制；
- 保留本期身份、团队与推广成果记录；
- 后续新活动可重新申请核心大使或加入新团队。

## 5. PC 运营后台逻辑

核心大使计划应接入**现有 PC 管理端控制面**，不另起一套独立后台。

首版运营心智保持三层：

```text
活动列表
→ 活动详情
→ 团队详情
```

活动配置与活动条款属于该运营工作台内的配置能力，不新增第二套后台。

### 5.1 活动列表

至少展示：活动名称、时间、状态、覆盖学校数、核心大使数、已点亮团队数、有效新增总数。

### 5.2 创建 / 编辑活动

创建与编辑使用同一套活动配置交互，首版采用现有 PC 公用 Modal，不切换到独立整页表单，也不另造新的弹层体系。

首版配置：

- 活动名称；
- 开始 / 结束时间；
- 参与学校；
- 大使申请表；
- 活动条款版本。

#### 参与学校

- 使用多选下拉；
- 支持一次选择多所学校；
- 编辑活动时回显已选学校；
- 活动与学校仍保持一对多关系，每所学校独立生成学校大使招募码。

#### 大使申请表

首版提供**轻量表单设计器**，只服务核心大使申请场景，不建设通用低代码表单平台。

支持：

- 新增 / 删除字段；
- 字段上下排序；
- 字段名称；
- 字段类型：单行文本、长文本、单选、多选；
- 必填 / 非必填；
- 单选、多选的选项配置；
- 最小必要预览。

保存后，学生 App 按该结构渲染本期申请表。

团队点亮门槛首版固定为「1 位核心大使 + 3 位推广伙伴」，不做复杂规则配置器。

### 5.3 活动条款库与版本规则

活动条款不作为活动表单中的一段临时文本维护，而作为运营工作台中的独立版本化内容管理。

首版规则：

- 每份条款有稳定 ID 和面向运营可读的版本号；
- 条款存在「草稿 / 已发布」状态；
- 运营可使用富文本编辑草稿；
- 已发布版本不可直接覆盖修改；
- 如需修改，必须从旧版本复制或新建新版本，再次发布；
- 创建 / 编辑活动时只能选择**已发布版本**，不要求运营手填技术 ID；
- 活动开始后，当期绑定的条款版本锁定，不随条款库后续版本变化；
- 学生申请记录保存其实际同意的条款版本。

首版正式发布版本为：

> **《核心大使计划活动条款》v1.0**

正文至少覆盖：

1. 参与资格与核心大使 / 推广伙伴身份说明；
2. 同一期活动中同一用户只能属于一个团队；
3. 活动期间不可主动退队或换队；
4. 团队点亮条件与点亮前后权限；
5. 团队招募码、专属推广码的用途边界；
6. 有效新增的计算口径；
7. 活动结束后的团队、招募码、推广码处理；
8. 推广成果与团队激励说明；
9. 为完成申请、组队、推广归因与成果统计所需的必要数据使用说明。

### 5.4 学校与大使招募码

- 每所学校生成独立的大使招募二维码；
- 二维码关联「活动 + 学校」；
- 二维码必须进入对应学校的**核心大使申请链路**，不得进入团队加入链路；
- 二维码卡片应包含适度的活动 / 学校识别信息，不使用纯通用占位块；
- 支持点击二维码卡片查看大图；
- 大图在 Modal 中展示，并支持下载；
- 可查看该学校产生的大使、团队与推广数据。

### 5.5 活动详情

顶部展示活动整体数据：覆盖学校、核心大使、已点亮团队、推广伙伴、有效新增。

下方团队列表至少包含：核心大使、学校、团队状态、团队人数、有效新增、激励状态，并提供基础筛选。

### 5.6 团队详情

展示：

- 核心大使基本信息和申请信息；
- 学校、团队状态、团队人数；
- 团队有效新增总数；
- 成员列表及每人有效新增；
- 必要推广明细；
- 简单团队激励状态。

运营端可查看成员级推广成果；推广伙伴 App 端不可查看。

### 5.7 团队激励

平台首版只负责：

- 提供团队推广成果；
- 识别对应核心大使；
- 如业务需要，记录简单的「未处理 / 已处理」状态。

平台不计算团队内部个人分成，不给推广伙伴逐人结算，也不干预大使如何分配激励。

## 6. 前后台联动

| 事件 | App 结果 | PC 结果 |
| --- | --- | --- |
| 创建活动并配置学校 / 申请表 / 条款版本 | 对应学校招募码可进入本期申请链路，并按本期配置展示申请表与条款版本 | 生成活动、学校与招募码，保存申请表结构和条款版本 |
| 大使申请成功 | 显示「待点亮」并获得团队招募码，同时记录实际同意的条款版本 | 新增大使与团队记录 |
| 推广伙伴加入 | 团队人数和点亮进度变化 | 团队人数同步变化 |
| 团队达到 4 人 | 大使变为「已点亮」，全员开放专属推广码 | 团队变为推广中 / 已点亮 |
| 新用户有效注册 | 大使端推广成果更新 | 活动 / 团队 / 成员数据同步更新 |
| 活动结束 | 二维码失效、团队结束、历史保留 | 活动和团队转历史状态 |

## 7. 首版不复杂化

- 不做多级代理、上下级大使或子团队；
- 不做推广伙伴排行榜；
- 不做活动期间退队 / 换队；
- 不做永久大使等级；
- 不做真实财务结算与个人分账；
- 不把推广成果混入赛事成绩 / 赛事身份；
- 不建设通用低代码表单平台；
- 不建设复杂条款审批流；
- 不新建与现有账号、学校、PC 控制面冲突的第二真相源。

## 9. 原型操作说明

本节用于产品评审、运营演示和人工验收。描述的是当前中保真原型中**如何把完整业务链实际走一遍**，不把原型专用模拟能力视为正式产品能力。

### 9.1 演示前准备

建议同时打开：

- PC 运营管理端；
- Mobile 原型窗口。

如需验证 PC / Mobile 同一业务状态，优先从 PC「核心大使计划」工作台进入**中保真联动预演**，由 PC 打开对应 Mobile 预演窗口。该模式用于原型跨端验收，不代表生产环境的数据同步方式。

活动状态按开始时间 / 结束时间自动判断：

- 未到开始时间：未开始；
- 时间区间内：进行中；
- 超过结束时间：已结束。

因此人工验收申请、组队和推广时，应使用处于「进行中」的活动。

### 9.2 PC：创建一期核心大使计划

1. 进入 PC 管理端「核心大使计划」；
2. 点击「创建活动」；
3. 在公用 Modal 中填写：
   - 活动名称；
   - 开始 / 结束时间；
   - 参与学校；
   - 大使申请表；
   - 已发布活动条款版本；
4. 「参与学校」可一次选择多所学校；
5. 在申请表设计器中可新增、删除、排序字段，并设置单行文本、长文本、单选、多选及必填状态；
6. 保存活动后进入活动详情。

如需演示条款版本管理，可先进入活动条款维护入口：

```text
已发布版本
→ 从旧版本创建草稿 / 新建版本
→ 编辑正文
→ 发布
→ 新活动选择该已发布版本
```

已发布版本不直接覆盖修改。

### 9.3 PC：获取学校大使招募二维码

1. 在活动详情找到对应学校的招募二维码；
2. 点击二维码卡片，可打开大图 Modal；
3. 可下载二维码用于演示或线下物料；
4. 每所学校二维码独立，扫码后应直接进入该活动、该学校的核心大使申请流程。

注意：**学校招募码只用于申请核心大使，不用于加入推广团队。**

### 9.4 App：模拟学生扫描学校招募码

当前原型不要求真实摄像头扫码。人工验收时：

1. 打开 Mobile「我的」；
2. 点击资料卡上的通用扫一扫入口；
3. 打开「扫一扫 · 原型模拟」；
4. 选择一个用于本次演示的学生账号；
5. 选择「学校招募码」并扫描当前活动对应学校的码；
6. 系统应直接进入核心大使申请页，不经过“选择申请大使还是加入团队”的混合页面。

「扫一扫 · 原型模拟」是人工验收工具，不属于正式用户功能。

### 9.5 App：提交核心大使申请

在申请页：

1. 确认活动与学校信息；
2. 按 PC 当前活动配置填写申请表；
3. 点击「核心大使计划活动条款」标题，查看正式条款正文；
4. 返回申请页，勾选同意条款；
5. 提交申请。

提交成功后应观察到：

- 当前账号成为「核心大使 · 待点亮」；
- 「我的」资料卡出现灰色「核心大使」身份标识；
- 「我的」服务区出现「我的团队」入口；
- 进入「我的团队」后可看到组队进度与真实团队招募二维码。

### 9.6 App：招募 3 位推广伙伴并点亮团队

1. 以核心大使身份进入「我的团队」；
2. 点击团队招募二维码可查看大图，并可长按保存 / 下载；
3. 再次使用「扫一扫 · 原型模拟」切换为第 1 位推广伙伴；
4. 选择「团队招募码」；
5. 扫描该核心大使的团队招募码；
6. 在邀请确认页确认：邀请人、活动、学校、加入身份「推广伙伴」及活动期间不可退队 / 换队；
7. 点击「确认加入」；
8. 依次切换第 2、3 位推广伙伴重复以上步骤。

当第 3 位推广伙伴加入后，团队达到：

> 1 位核心大使 + 3 位推广伙伴

此时应自动点亮，无需运营手工审批。

点亮后检查：

- 核心大使状态变为「已点亮」；
- 核心大使获得个人专属推广码；
- 3 位推广伙伴分别获得自己的专属推广码；
- 推广伙伴视角看不到团队有效新增、其他成员成果或排行榜。

### 9.7 App：验证点亮后仍可继续招募

为验证“4 人只是最低门槛，不是人数上限”：

1. 切换第 4 位推广伙伴；
2. 再次扫描同一团队招募码；
3. 确认加入；
4. 新伙伴加入后应立即获得自己的专属推广码；
5. 团队继续保持已点亮状态。

### 9.8 App：模拟专属推广码带来有效新增

1. 选择任意一位已获得专属推广码的成员；
2. 展示 / 打开其个人专属推广二维码；
3. 在通用扫一扫原型模拟中选择「专属推广码」；
4. 使用一个此前未注册过 App 的测试用户完成注册模拟；
5. 注册成功后，该有效新增应归因到对应活动、团队和推广人员。

重复扫码或使用已注册账号，不应重复增加有效新增。

### 9.9 App：检查核心大使与推广伙伴权限

以核心大使身份进入团队推广成果：

- 可看团队有效新增总数；
- 可看各成员对应有效新增；
- 可查看运营允许展示的必要推广明细。

再切换任意推广伙伴：

- 可看自己所属团队与当前活动状态；
- 可看自己的专属推广码；
- 不应看到自己的有效新增数量；
- 不应看到团队总新增；
- 不应看到其他成员成果或成员级明细。

### 9.10 PC：检查前后台联动与团队激励

完成 App 申请、组队、点亮和有效新增后，返回 PC：

1. 打开同一期活动详情；
2. 核对核心大使数、已点亮团队数、推广伙伴数、有效新增；
3. 进入对应团队详情；
4. 核对核心大使申请信息、成员、团队状态及成员级有效新增；
5. 如本期启用团队激励状态，可将该团队从「未处理」更新为「已处理」。

激励只记录到核心大使对应团队，不在原型中给推广伙伴逐人分账。

### 9.11 验证活动结束与历史保留

活动结束状态由结束时间自动生效。使用已结束活动或把验收活动配置到可形成结束态的时间范围后，检查：

- 学校招募码明确提示活动已结束 / 不可申请；
- 团队招募码不可继续加入；
- 专属推广码不可继续形成有效新增；
- 团队状态转为历史 / 已结束；
- 已有申请、成员、推广成果和激励状态仍保留；
- 旧团队不再阻止同一账号参加下一期核心大使计划。

### 9.12 推荐完整演示顺序

一次完整产品评审建议按以下顺序连续演示：

```text
PC 创建活动
→ 配置学校 / 申请表 / 已发布条款
→ 查看学校招募二维码
→ 开启中保真联动预演
→ App 扫学校码
→ 提交核心大使申请
→ 我的：灰色核心大使标识 + 我的团队
→ 展示团队招募二维码
→ 3 位推广伙伴依次扫码加入
→ 团队自动点亮
→ 第 4 位伙伴继续加入
→ 展示全员个人专属推广码
→ 新用户通过其中一个推广码完成注册模拟
→ 核心大使查看团队推广成果
→ 切换推广伙伴验证成果数字隔离
→ PC 查看同步后的团队 / 成员 / 有效新增
→ 处理团队激励
→ 验证活动结束、二维码失效、历史保留与下一期可重新参加
```

### 9.13 原型模拟能力边界

以下能力仅用于中保真验收，不应被研发理解为正式产品需求：

- 「扫一扫 · 原型模拟」中的账号切换；
- 预置的多位推广伙伴测试身份；
- PC「中保真联动预演」窗口与跨窗口 demo state 同步；
- 前端模拟新用户注册及有效新增归因。

正式实现时应替换为真实登录账号、真实扫码 / Deep Link、服务端活动与团队状态、安装 / 注册归因和后台数据同步，但业务规则与权限边界保持本 PRD 定义不变。
