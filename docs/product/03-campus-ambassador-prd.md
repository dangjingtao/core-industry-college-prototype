# 03｜核心大使计划 PRD

> 状态：Draft / 待评审  
> 适用：学生 App + 运营后台  
> 目标：把「核心大使计划」从招募、组队、推广到运营结算整理为一套可直接设计、开发和验收的首版逻辑。

---

## 1. 需求目标

运营方通过「核心大使计划」在学校内发展学生推广团队。

首版完成四件事：

1. 运营方创建一期推广活动，并向指定学校投放大使招募二维码；
2. 核心大使申请加入计划，招募推广伙伴并完成团队激活；
3. 团队激活后，全员通过各自专属推广码带来新用户注册；
4. 核心大使查看团队推广成果，运营方查看全局数据并处理团队激励。

本功能按「一期推广活动」运行。活动结束后团队自动结束，二维码失效，只保留历史记录。

---

## 2. 角色与用词

### 2.1 运营方

负责创建活动、投放学校招募码、查看团队与推广成果、记录团队激励。

### 2.2 核心大使

每个推广团队仅有 1 位核心大使。

- 通过学校招募二维码申请加入计划；
- 负责招募推广伙伴；
- 团队激活后参与推广；
- 可查看本团队推广成果；
- 运营方的团队激励发放给核心大使，平台不干涉团队内部如何分配。

### 2.3 推广伙伴

通过核心大使的「团队招募码」加入团队。

- 可以是 App 新用户；
- 也可以是已注册、但尚未加入本期其它推广团队的老用户；
- 团队激活后获得自己的专属推广码；
- 可以参与推广；
- 不查看个人或团队推广成果。

### 2.4 统一用词

- 活动：**核心大使计划**
- 大使状态：**核心大使 · 待点亮 / 已点亮**
- 普通团队成员：**推广伙伴**
- 大使用于组队的二维码：**团队招募码**
- 全员用于拉新的二维码：**专属推广码**
- 原「业绩」：统一称为 **推广成果**
- 成功拉新的统计指标：**有效新增**
- 运营方给予大使的奖励：**团队激励**

---

## 3. 整体业务流程

```text
【运营后台】
创建核心大使计划
→ 选择学校 / 配置活动时间
→ 生成各学校大使招募二维码
        ↓

【学生 App】
学生扫描学校招募码
→ 登录 / 注册
→ 填写大使申请表 + 同意条款
→ 获得「核心大使 · 待点亮」
→ 获得团队招募码
→ 邀请推广伙伴加入团队
→ 1 位核心大使 + 至少 3 位推广伙伴
→ 团队激活
→ 「核心大使 · 已点亮」
→ 团队全员获得各自专属推广码
→ 推广码 → 下载 App → 新用户注册成功
→ 形成有效新增
        ↓

【学生 App】
核心大使查看本团队推广成果
推广伙伴只负责推广，不查看成果数据
        ↓

【运营后台】
查看活动 / 学校 / 团队推广成果
→ 按活动规则处理团队激励
        ↓

活动结束
→ 团队自动结束
→ 招募码 / 推广码失效
→ 保留历史活动、团队和推广成果记录
```

## 4. 学生 App 逻辑

### 4.1 核心大使申请

运营方向每个参与学校提供对应的「大使招募二维码」。

学生扫码后：

1. 未登录用户先完成登录或注册，完成后回到申请流程；
2. 填写运营要求的申请字段；
3. 阅读并勾选相关条款；
4. 提交成功后立即获得核心大使资格，不增加人工审核步骤；
5. 初始身份显示为「核心大使 · 待点亮」；
6. 系统生成该大使的「团队招募码」。

同一用户在同一期活动中只能属于一个推广团队，不能同时成为其它团队的推广伙伴或再次申请成为核心大使。

### 4.2 招募推广伙伴

核心大使分享「团队招募码」。

用户扫码后：

- 新用户可以注册后加入；
- 已注册老用户可以直接加入；
- 前提是该用户尚未加入本期其它推广团队；
- 加入成功后成为该团队的「推广伙伴」。

活动进行期间，团队关系不可主动退出、不可换队。

团队人数不设 4 人上限。达到激活条件后，大使仍可继续邀请更多推广伙伴。

### 4.3 团队激活

团队激活条件：

> **1 位核心大使 + 至少 3 位推广伙伴，即团队总人数达到 4 人。**

激活前：

- 核心大使显示「待点亮」；
- 页面显示当前组队进度；
- 只开放团队招募；
- 不开放正式推广；
- 不启用任何人的专属推广码。

激活后：

- 核心大使显示「已点亮」；
- 团队进入「推广中」；
- 核心大使与全部推广伙伴获得各自独立的「专属推广码」；
- 后续新加入的推广伙伴，加入已激活团队后也获得自己的专属推广码。

### 4.4 专属推广码与有效新增

每位核心大使和推广伙伴拥有独立的专属推广码。

```text
专属推广码
→ 用户扫码
→ 进入 App 下载流程
→ 安装 App
→ 完成新用户注册
→ 系统识别推广来源
→ 计为对应推广人员的 1 个有效新增
```

业务口径：

- 系统需要从扫码开始保留推广来源；
- 仅此前未注册过 App 的新用户注册成功，计为有效新增；
- 已注册用户再次扫码不计为新增；
- 每个有效新增需要能够关联到：活动、团队、推广人员；
- 安装归因的具体技术方案由研发确定，PRD 不锁定实现方式。

### 4.5 推广成果查看权限

#### 核心大使

拥有「团队推广成果」入口，可查看：

- 当前团队人数；
- 团队有效新增总数；
- 核心大使及各推广伙伴对应的有效新增数量；
- 运营最终确认需要展示的推广明细。

#### 推广伙伴

可以看到：

- 自己已加入哪个团队；
- 当前活动 / 团队状态；
- 团队激活后的个人专属推广码。

不展示：

- 自己的有效新增数量；
- 其他成员的推广成果；
- 团队有效新增总数；
- 推广排行榜。

### 4.6 活动结束后的 App 表现

活动到达结束时间后：

- 团队自动结束；
- 团队招募码、专属推广码停止生效；
- 不再新增推广成果；
- 用户解除本期活动的团队绑定限制；
- 保留本期核心大使身份记录、团队记录和推广成果记录；
- 后续新活动可重新申请核心大使或加入新团队。

## 5. 运营后台逻辑

后台首版不拆成复杂系统，围绕「活动 → 团队 → 推广成果」三层展开。

### 5.1 活动列表

「核心大使计划」作为运营后台的一个业务模块。

活动列表至少展示：

- 活动名称；
- 活动时间；
- 活动状态；
- 覆盖学校数量；
- 核心大使数量；
- 已激活团队数量；
- 有效新增总数。

运营方可以进入某一期活动详情。

### 5.2 创建 / 编辑活动

首版活动配置包括：

- 活动名称；
- 开始时间；
- 结束时间；
- 参与学校；
- 大使申请表字段；
- 用户需要确认的活动条款；
- 团队激活门槛首版固定为「1 位核心大使 + 3 位推广伙伴」。

活动时间到达后按配置进入对应状态；活动结束后自动停止招募和推广。

### 5.3 学校与大使招募码

每个活动下，运营方可以维护参与学校。

每个学校生成独立的「大使招募二维码」，便于运营方将二维码交给对应学校的特定学生或推广渠道。

后台至少支持：

- 查看学校；
- 查看 / 下载该学校的大使招募二维码；
- 查看该学校通过此活动产生的核心大使和推广数据。

二维码需要关联「活动 + 学校」，避免不同活动、不同学校的数据混在一起。

### 5.4 活动详情

活动详情作为运营主要工作页，首版不额外拆很多菜单。

顶部展示活动整体数据，例如：

- 覆盖学校；
- 核心大使数量；
- 已激活团队数量；
- 推广伙伴数量；
- 有效新增总数。

下方提供团队列表。

团队列表至少展示：

| 字段 | 说明 |
| --- | --- |
| 核心大使 | 团队负责人 |
| 学校 | 大使申请来源学校 |
| 团队状态 | 组建中 / 推广中 / 已结束 |
| 团队人数 | 大使 + 推广伙伴 |
| 有效新增 | 团队累计推广成果 |
| 激励状态 | 未处理 / 已处理（如首版启用） |

支持按学校、团队状态等基础条件筛选。

### 5.5 团队详情

点击团队进入团队详情。

展示：

- 核心大使基本信息和申请信息；
- 学校；
- 团队状态；
- 团队人数；
- 团队有效新增总数；
- 团队成员列表；
- 每位成员对应的有效新增数量；
- 必要的新增明细。

运营后台可以查看成员数据；学生端推广伙伴不可查看这些成果数据。

### 5.6 团队激励

运营方根据活动规则向核心大使提供团队激励。

首版平台只负责：

- 提供团队推广成果作为运营判断依据；
- 识别对应核心大使；
- 如业务需要，记录「未处理 / 已处理」等简单激励状态。

平台不负责：

- 计算团队内部每个人应分多少；
- 给推广伙伴逐人结算；
- 干预核心大使与推广伙伴之间的分配方式。

## 6. App 与后台联动规则

| 后台 / 系统事件 | App 侧结果 |
| --- | --- |
| 创建活动并配置学校 | 对应学校可以生成大使招募码 |
| 用户完成大使申请 | 后台新增核心大使 / 团队记录；App 显示「待点亮」 |
| 推广伙伴加入团队 | 后台团队人数增加；App 同步更新组队进度 |
| 团队总人数达到 4 人 | 团队自动激活；大使点亮；全员开启专属推广码 |
| 新用户通过专属推广码完成注册 | 后台累计对应成员与团队有效新增；大使端团队成果同步更新 |
| 运营查看 / 处理团队激励 | 只更新后台运营记录，不改变团队内部成员分配 |
| 活动结束 | App 团队结束、二维码失效；后台转为历史活动并保留数据 |

核心原则：

> **后台管理活动与数据，App 承载学生参与行为；两端读取同一套活动、团队、成员和推广成果状态。**

---

## 7. 状态定义

### 活动状态

| 状态 | 含义 |
| --- | --- |
| 未开始 | 已创建，但尚未到活动开始时间 |
| 进行中 | 可以申请、组队和推广 |
| 已结束 | 停止申请、组队和新增推广成果 |

### 核心大使状态

| 状态 | 含义 |
| --- | --- |
| 待点亮 | 已完成申请，但团队人数不足 4 人 |
| 已点亮 | 团队达到激活条件 |
| 已结束 | 本期活动结束 |

### 团队状态

| 状态 | 含义 |
| --- | --- |
| 组建中 | 团队总人数不足 4 人 |
| 推广中 | 团队已激活，可正式推广 |
| 已结束 | 活动结束，团队关系终止 |

---

## 8. 页面范围

### 学生 App

首版控制在少量页面：

1. **大使申请页**：申请字段、条款、提交；
2. **核心大使页**：身份状态、组队进度、团队招募码、个人推广码、团队推广成果入口；
3. **团队推广成果页**：仅核心大使可见；
4. **推广伙伴活动状态页**：所在团队、活动状态、激活后的个人推广码。

### 运营后台

首版控制在三层：

```text
核心大使计划活动列表
→ 活动详情（学校招募码 + 整体数据 + 团队列表）
→ 团队详情（成员 + 推广成果 + 激励状态）
```

不为首版拆出复杂的独立「推广中心」「结算中心」或多层级代理后台。

---

## 9. 首版暂不复杂化

- 不做多级代理或上下级推广关系；
- 推广伙伴不能建立子团队；
- 活动期间不支持退队、换队；
- 不做学生端排行榜；
- 不向推广伙伴展示个人推广成果；
- 不在 App 内处理团队激励分账；
- 不把核心大使做成永久等级体系；
- 不增加大使人工审核流程；
- 后台先以活动详情为核心，不拆大量菜单。

---

## 10. 待运营确认

进入 UI / 开发前还需补齐：

1. 大使申请表的具体字段；
2. 用户需要同意的协议 / 条款；
3. 首期活动开始和结束时间；
4. 团队激励的具体规则，以及是否需要后台记录发放金额；
5. 「推广明细」最终需要展示到什么粒度。

其余角色关系、团队激活条件、App / 后台权限和推广成果口径按本文执行。
