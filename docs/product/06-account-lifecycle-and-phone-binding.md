# 06｜账号生命周期、赛事自动开通与手机号换绑设计

> 状态：Current Design / T028 施工依据  
> 日期：2026-08-24  
> 适用：核心学院 App、PC 三创赛报名门户、后续其它赛事接入  
> 关联：T028、T029、T015、T015R1、F01、F03

---

## 1. 已确认产品原则

以下为 Owner 已确认规则：

1. **队长在 PC 端登录 / 注册并完成团队报名。**
2. 队长提交团队资料后，先进入学校审核；**审核通过后才进入成员账号创建 / 赛事身份绑定流程。**
3. 审核通过后：
   - 未注册核心学院的队员，自动生成核心学院 App 的待激活账号；
   - 已注册核心学院的队员，按手机号命中原长期账号，并自动关联本次赛事身份；
   - 系统发送业务通知短信，并同时保留站内通知 / 登录提示。
4. **手机号是当前唯一硬匹配凭证。**
   - 姓名、学校、学号不是账号绑定的强制条件；
   - 这些字段如果存在，可以做风险提示和人工核验辅助，但不能因为缺失就阻断账号绑定。
5. **团队减员不影响核心学院长期账号。**
6. **赛事时间之外允许自助换绑手机号；赛事进行中普通自助换绑受限，保留人工高风险换绑通道。**
7. 新手机号已被其它账号使用时，不自动合并账号或迁移资产。

## 2. 核心数据语义

### 2.1 UserAccount｜长期账号

长期账号必须有稳定 `userId`：

```text
UserAccount
  ├─ userId                    // 稳定，不随手机号变化
  ├─ accountStatus
  ├─ loginIdentifiers
  │    ├─ phone               // 当前主要登录与匹配凭证
  │    ├─ wechat              // 可选绑定
  │    └─ password / passkey  // 可选登录凭证
  ├─ StudentProfile
  ├─ CompetitionIdentity[]
  └─ LongTermAssets
```

**手机号不是不可变账号主键。**

未来允许换绑手机号，因此证书、课程、赛事身份、简历等必须归属于 `userId`，不能归属于手机号。

### 2.2 CompetitionIdentity｜赛事身份

```text
CompetitionIdentity
  ├─ userId
  ├─ competitionId
  ├─ teamId
  ├─ role
  ├─ registrationStatus
  ├─ identityStatus
  ├─ assignmentSource
  └─ acknowledgementStatus
```

推荐：

```text
assignmentSource = school_approved_team
acknowledgementStatus = unconfirmed | confirmed | disputed
```

“自动绑定”与“本人已经确认”必须区分。

### 2.3 TeamMembership｜团队关系

```text
TeamMembership: active → removal_pending → removed
CompetitionIdentity: active → revoked / removed
UserAccount: 保持 active
LongTermAssets: 保持不变
```

减员只改变本赛事关系，不删除用户、不注销 App、不影响其它赛事。

## 3. 正确的账号创建触发点

### 3.1 团队提交阶段

```text
队长提交团队资料
→ 保存赛事团队成员记录
→ 基础格式 / 重复手机号校验
→ 进入学校审核
```

此时：

- **不创建新长期账号**；
- **不向已有账号绑定赛事身份**；
- 不发送“账号已开通”短信；
- 可以发送“团队报名已提交审核”等赛事流程通知。

这样可避免学校审核前因为误录、撤回、驳回产生大量脏账号。

### 3.2 学校审核通过阶段

学校审核通过后触发一次 Account Resolution：

```text
school_review = approved
→ 遍历团队成员手机号
→ 查询长期账号
→ 创建 / 绑定赛事身份
→ 写入通知事件
```

---

## 4. 审核通过后的成员账号解析

### A. 手机号未命中任何长期账号

系统动作：

1. 创建稳定 `userId`；
2. 创建 `provisioned_unclaimed` 待激活账号；
3. 创建本次 `CompetitionIdentity`；
4. 数据来源标记为 `school_approved_team`；
5. 发送业务服务短信；
6. 用户首次进入 App 时用该手机号验证码认领同一个 `userId`。

推荐短信语义：

> 你所在团队的赛事报名已通过学校审核，核心学院账号已为你开通。使用本手机号验证后可进入 App 查看赛事信息。

不要设置公共默认密码。

### B. 手机号命中一个已有长期账号

手机号是唯一硬匹配条件。

系统动作：

1. 不创建第二个账号；
2. 在原 `userId` 下增加本次 `CompetitionIdentity`；
3. `assignmentSource = school_approved_team`；
4. `acknowledgementStatus = unconfirmed`；
5. 发送业务短信；
6. 写入持久化站内通知。

姓名、学校、学号：

- 不要求必须存在；
- 不作为强绑定条件；
- 如果存在且明显异常，可以产生风险提示，但不默认取代手机号匹配逻辑。

### C. 手机号账号层面存在真正冲突

“冲突”不再定义成“姓名 / 学号不一致”，而是账号系统自身无法唯一确定归属，例如：

- 历史迁移导致同一手机号命中多个账号；
- 新旧账号合并状态异常；
- 手机号被风控锁定；
- 后台存在尚未完成的账号迁移 / 恢复工单。

此时：

```text
account_resolution = conflict
```

不自动创建第二账号，不自动迁移资产，进入人工核验。

### D. 同一团队重复手机号

在学校审核前即可阻止：

- 同一手机号被填入两个成员；
- 同一成员记录被重复提交。

这是报名数据错误，不需要等到账号创建阶段处理。

---

## 5. 自动绑定后的误绑兜底

因为姓名 / 学号不是硬绑定条件，必须承认一种风险：队长可能填错手机号。

因此已有账号自动挂赛事身份后，应始终保留：

> **“这不是我的参赛信息 / 需要核对”**

点击后：

```text
acknowledgementStatus: unconfirmed → disputed
→ 暂停该赛事身份的高风险操作
→ 生成客服 / 赛事核验工单
→ 不影响用户其它 App 功能和其它赛事身份
```

用户不需要主动点击“确认”才能完成会议要求中的自动绑定；`acknowledgementStatus` 主要用于纠错与审计。

## 6. 待激活账号与本人首次进入 App

### 6.1 账号状态

```text
provisioned_unclaimed  // 学校审核通过后自动创建，本人尚未验证
active                 // 本人完成手机号验证并激活
conflict               // 账号归属存在系统级冲突
suspended              // 后台治理状态
```

### 6.2 首次登录

```text
手机号验证码登录
→ 命中 provisioned_unclaimed
→ 告知“赛事审核通过后已为你开通账号”
→ 验证手机号
→ 展示个人信息处理说明 / 用户协议 / 隐私政策
→ 本人确认后激活长期平台账号
→ 展示本次赛事身份
→ 按需补齐长期资料
→ 进入 App
```

不重新注册第二个账号。

### 6.3 在本人激活前的能力边界

待激活账号只用于赛事必要服务：

- 保存审核通过所需的最低成员资料；
- 保存赛事身份与团队关系；
- 发送赛事 / 账号业务通知；
- 等待本人认领。

本人尚未激活时，不建议：

- 用于课程、就业、广告推荐画像；
- 自动订阅营销短信；
- 基于该账号扩展与赛事无直接关系的数据处理；
- 把队长填写的资料视为本人已确认的长期个人档案。

## 7. 合规设计提示（非法律意见）

这里存在一定个人信息合规风险，但风险可以通过产品边界明显降低。

### 7.1 风险不是“系统里存在一条账号记录”这么简单

队长向平台提交成员手机号等信息时，平台已经在处理个人信息。应在赛事报名规则 / 隐私告知中明确：

- 哪些成员信息会被收集；
- 用于团队报名、学校审核、赛事身份和账号开通；
- 核心学院 / 赛事运营主体是谁；
- 保存期限与用户权利入口。

《个人信息保护法》要求个人信息处理具有明确合理目的、采取最小必要方式，并在处理前履行告知义务；基于同意处理时，应当获得充分知情、自愿、明确的同意。

### 7.2 “赛事必要处理”与“长期平台服务”建议分层

学校审核通过后，为完成赛事服务而创建一个受限的待激活账号，风险相对可控；但核心学院还包含课程、机会、权益等长期平台业务，这些已经超出纯赛事报名语义。

因此推荐：

```text
审核通过
→ 自动建立赛事必要的 provisioned_unclaimed 账号
→ 本人首次登录
→ 完成手机号验证 + 隐私告知 / 协议确认
→ 才激活长期平台能力
```

不要把“队长提交成员资料”理解为队员已经对所有核心学院长期服务作出同意。

是否可以完全依赖“履行赛事合同所必需”作为无需本人同意的法律基础，需要结合赛事协议、参赛主体关系和实际运营主体由法务最终确认，产品文档不自行下法律结论。

### 7.3 短信必须保持业务服务属性

2026 年修订后的《通信短信息服务管理规定》区分商业性短信与“操作验证、系统登录、业务提醒”等业务管理和服务性短信。

本场景短信应只包含：

- 赛事审核结果；
- 账号开通 / 认领；
- 登录验证；
- 安全变更通知。

不要在同一短信中追加“课程推荐、福利、实习机会、优惠”等营销内容，以免把服务通知和商业营销混在一起。

### 7.4 长期无人认领账号需要退出机制

应保留：

```text
unclaimed_account_retention_policy
```

当赛事处理目的完成、保存期限届满或继续保存已无必要时，对非必须保留的数据删除或匿名化；不能让无人认领账号永久沉积。

## 8. 已有 App 用户收到赛事身份

```text
原账号正常登录
→ 读取未读站内通知
→ 展示“学校审核通过，你已加入 ×× 赛事 / ×× 团队”
→ CompetitionIdentity 已自动关联
```

通知提供：

- 查看赛事；
- 这不是我的参赛信息；
- 联系客服 / 核验。

不重新 onboarding。

## 9. 减员设计

### 减员申请中

成员仍保持当前团队和赛事权限，状态显示“减员审核中”。

### 减员审核通过

- `TeamMembership` → `removed`；
- 本赛事工作区权限回收；
- `CompetitionIdentity` 保留历史事实并标记 `revoked / removed`；
- `UserAccount` 保持 active；
- 其它赛事身份不受影响；
- 长期资产按赛事规则保留。

禁止：

- 注销 App 账号；
- 解绑手机号；
- 删除其它赛事身份；
- 把用户退回“未注册”。

## 10. 手机号换绑

### 10.1 赛事外自助换绑

“赛事时间之外”按**当前用户是否存在活跃赛事身份**判断，而不是按平台全局赛事日历判断。

```text
无报名 / 审核 / 正赛中的 CompetitionIdentity
→ 允许普通自助换绑
```

流程：

```text
已登录账号
→ 账号与安全
→ 更换手机号
→ 验证当前手机号
→ 验证新手机号
→ 检查新手机号账号占用
→ 更新 loginIdentifier.phone
→ userId / Profile / CompetitionIdentity / LongTermAssets 不变
→ 原手机号与新手机号发送安全通知
→ 其它设备会话失效
→ 完成
```

### 10.2 活跃赛事期间

```text
存在活跃赛事身份
→ 普通自助换绑暂停
→ App 其它功能继续正常
→ 紧急情况进入人工高风险换绑
```

### 10.3 新手机号已经绑定其它账号

禁止自动合并。

- 当前账号保持不变；
- 新手机号不覆盖旧账号；
- 进入人工核验；
- 证书、赛事身份、课程、简历不由前端自动迁移。

### 10.4 原手机号不可用

提供“无法使用原手机号”人工恢复入口。

可供后续风控设计参考的核验材料包括：

- 已绑定微信；
- 赛事资料；
- 学校 / 学号（如果有）；
- 已验证邮箱；
- 人工客服审核。

具体 KYC 强度后续确认。

### 10.5 换绑频率

保留后台可配置冷却期：

```text
phone_binding_change_cooldown_days
```

具体天数后续运营 / 风控确认。

## 11. PC 队长登录 / 注册

```text
队长进入 PC 报名门户
→ 手机号登录 / 注册
→ 命中核心学院长期账号则复用
→ 未注册则为队长本人创建长期账号
→ 填写团队与成员资料
→ 提交学校审核
→ 审核通过后系统处理所有队员账号
```

队员不再要求提前到 PC 注册。

推荐首期支持：

- 手机号 + 验证码；
- 手机号 + 密码（已设置密码用户）；
- 历史登录名仅作为迁移兼容入口。

邮箱继续作为赛事正式通知字段，不作为第二套长期账号主键。

## 12. 状态矩阵

| 场景 | 系统动作 | 账号 | 赛事身份 | App 使用 |
| --- | --- | --- | --- | --- |
| 团队刚提交 | 等待学校审核 | 不新建 | 不绑定 | 原状 |
| 审核驳回 | 返回修改 | 不新建 | 不绑定 | 原状 |
| 审核通过，手机号未注册 | 创建待激活账号 | provisioned_unclaimed | 自动创建 | 验证后激活 |
| 审核通过，手机号已有账号 | 复用原账号 | 不新建 | 自动新增，unconfirmed | 正常 |
| 用户称“不是我的赛事” | 建立核验工单 | 不变 | disputed | 其它功能正常 |
| 账号系统归属冲突 | 人工核验 | 不新建 | 暂停绑定 | 原账号正常 |
| 队员被减员 | 保留账号 | 不变 | revoked / removed | 正常 |
| 用户参加另一场赛事 | 复用原账号 | 不变 | identities[] 新增 | 正常 |
| 赛外换手机号 | 更新登录凭证 | userId 不变 | 全部保留 | 正常 |
| 活跃赛事期间换绑 | 普通自助阻止 | 不变 | 不变 | 正常 |
| 新手机号已占用 | 人工核验 | 不合并 | 不变 | 原账号正常 |

## 13. 仍需后续确认

1. 待激活账号具体保留多久，以及赛事结束后无人认领数据的删除 / 匿名化策略。
2. 活跃赛事期间人工换绑的身份核验标准。
3. 手机号换绑冷却期具体天数。
4. 同一手机号命中历史多账号时的归并 SOP。
5. 同一学生同一赛事是否存在允许多团队 / 多赛道的业务例外。
6. 最终赛事报名条款、隐私告知与“审核通过后自动创建待激活账号”的合规文本，由业务 / 法务确认。

## 14. 当前施工验收底线

- 团队提交时不能提前创建队员账号；
- 只有学校审核通过后执行成员账号解析；
- 姓名 / 学校 / 学号不能作为账号绑定必填条件；
- 已有账号按手机号复用，不创建第二账号；
- 新账号先进入 `provisioned_unclaimed`；
- 本人激活前只处理赛事必要用途；
- 赛事减员不能导致公共平台账号失效；
- 手机号换绑后所有长期资产仍归属同一 `userId`；
- 误填手机号必须有“不是我的赛事”纠错入口；
- 服务短信不得夹带营销内容。
