# 06｜账号生命周期、赛事自动开通与手机号换绑设计

> 状态：Current Design Draft / T028 施工依据  
> 日期：2026-08-24  
> 适用：核心学院 App、PC 三创赛报名门户、后续其它赛事接入  
> 关联：T028、T029、T015、T015R1、F01、F03  

---

## 1. 本轮会议已确认原则

以下内容作为本轮产品决策，不再由施工线程自行改写：

1. **队长在 PC 端登录 / 注册并完成团队资料。**
2. 团队成员名单进入正式提交后：
   - 未注册核心学院的队员，自动获得核心学院 App 账号；
   - 已注册核心学院的队员，自动关联本次赛事参赛身份；
   - 通过短信提醒，或在用户后续登录时以站内提示告知。
3. **团队减员不影响核心学院长期账号本身。**
   - 赛事团队关系可以结束；
   - App 账号、课程、权益、长期经历等公共平台能力继续存在。
4. **赛事时间之外允许用户自助换绑手机号。**
   - 换绑手机号不应产生新账号；
   - 原账号的长期资产与历史赛事身份继续归属于同一个人。

---

## 2. 必须先固定的数据语义

### 2.1 UserAccount｜长期账号

长期账号必须有稳定 `userId`。

手机号不是账号本体，而是一个可验证、可更换的登录凭证：

```text
UserAccount
  ├─ userId                    // 稳定，不随换手机号变化
  ├─ loginIdentifiers
  │    ├─ phone               // 当前已验证手机号
  │    ├─ wechat              // 可选绑定
  │    └─ password / passkey  // 可选登录凭证
  ├─ StudentProfile
  ├─ CompetitionIdentity[]
  └─ LongTermAssets
```

**禁止使用手机号本身作为不可变账号主键。**

原因：会议已经确认未来允许换绑手机号；如果手机号就是账号主键，换绑会天然演变成“迁移账号”，随后证书、课程、赛事身份、简历都会产生归属风险。

### 2.2 CompetitionIdentity｜赛事身份

赛事身份属于具体赛事生命周期：

```text
CompetitionIdentity
  ├─ userId
  ├─ competitionId
  ├─ teamId
  ├─ role
  ├─ registrationStatus
  ├─ identityStatus
  └─ membershipStatus
```

同一个长期账号可以拥有多场赛事身份。

### 2.3 TeamMembership｜团队成员关系

团队成员关系与 App 账号必须分离。

减员时：

```text
TeamMembership: active → removed
CompetitionIdentity: active → revoked / removed
UserAccount: 保持 active
LongTermAssets: 保持不变
```

不删除用户，不清空资料，不注销 App，不抹掉历史记录。

## 3. 队长提交团队后的账号解析流程

### 3.1 触发点修正

会议口径中的“上传团队资料后自动获得账号”，产品实现上不建议绑定到每一次草稿保存或附件上传。

建议正式触发点为：

> **队长提交团队成员名单，且成员基础字段通过前置校验后。**

原因：草稿阶段可能频繁增加 / 删除成员、手机号尚未确认、存在复制粘贴错误。如果草稿一保存就真正建号，会产生大量无人认领的脏账号和重复短信。

### 3.2 成员解析状态

每一名成员提交时进入一次 Account Resolution：

#### A. 未命中长期账号

条件：当前手机号未绑定任何长期账号。

系统动作：

1. 创建稳定 `userId`；
2. 创建“已预开通、待本人认领”的长期账号；
3. 将本次赛事身份挂到该 `userId`；
4. 记录资料来源为“赛事队长提交”；
5. 发送账号开通短信；
6. 用户首次进入 App 时使用手机号验证码认领，不需要队长设置默认密码。

用户体验文案应表达为：

> 你的核心学院账号已由赛事报名自动开通，验证手机号即可继续使用。

不使用公共默认密码，不要求队员提前再去 PC 注册一遍。

#### B. 命中已有长期账号，且身份字段一致

条件建议至少满足：

- 手机号命中；
- 姓名一致或可解释；
- 学校 / 学号等赛事实名字段无明显冲突。

系统动作：

1. 不创建第二个账号；
2. 在原 `userId` 下增加本次 `CompetitionIdentity`；
3. 发送短信通知；
4. 同时创建一条持久化站内通知，确保短信失败或用户换设备后仍可看到。

因此这里建议不是“短信 **或** 登录弹窗”二选一，而是：

```text
事件发生
→ 尝试短信提醒
→ 同时写入站内通知
→ 用户下次登录 / 当前在线时展示
```

#### C. 手机号命中已有账号，但身份信息明显冲突

典型场景：

- 队长手机号录错；
- 号码已二次放号；
- 现有账号姓名 / 学校与报名成员完全不一致。

系统不得自动绑定赛事身份。

进入：

```text
account_resolution = conflict
```

处理方式：

- 队长修正成员信息；或
- 运营 / 客服人工核验。

**禁止因为手机号相同就自动把赛事身份塞进一个可能属于陌生人的账号。**

#### D. 同一赛事内出现重复归属

以下情况应在团队提交前直接阻止：

- 同一手机号被填写为两名成员；
- 同一 `userId` 已属于同一赛事另一支互斥团队；
- 同一实名学生被重复录入。

不把这类问题留到 App 首次登录时才发现。

---

## 4. “自动获得 App 账号”不等于“账号已经被本人确认”

系统可以先开通长期账号，但必须区分：

```text
provisioned_unclaimed  // 赛事报名自动开通，本人尚未验证
active                 // 本人已验证并正常使用
conflict               // 身份存在冲突，暂停自动归并
suspended              // 后台治理状态，非赛事减员
```

`provisioned_unclaimed` 已经拥有稳定 `userId` 和赛事身份，但在本人首次验证码验证前：

- 不允许修改高风险资料；
- 不允许进行手机号换绑；
- 不应被视为“已完成本人实名确认”。

这既满足“自动获得账号”，又避免把队长录入的数据当成本人已经确认的事实。

## 5. 队员首次进入 App

### 5.1 自动开通的新队员

```text
手机号验证码登录
→ 命中 provisioned_unclaimed
→ 展示“赛事报名已为你开通账号”
→ 验证手机号
→ 认领同一个 userId
→ 展示新增赛事身份
→ 补齐缺失的长期个人资料
→ 进入 App
```

不重新注册第二个账号。

### 5.2 已有 App 用户

```text
原账号正常登录
→ 读取未读站内通知
→ 提示“你的账号已关联 ×× 赛事 / ×× 团队”
→ CompetitionIdentity[] 增加一项
```

不强制重新 onboarding。

### 5.3 用户认为“我没有参加这个团队”

通知中必须提供：

> “这不是我的参赛信息 / 需要核对”

进入客服 / 赛事身份申诉，而不是让用户自己删除赛事身份。

这是防止队长填错手机号时的重要兜底。

## 6. 减员设计

会议已明确：减员不影响 App 使用。

建议精确落成：

### 减员申请提交

成员仍保持当前团队和赛事权限，状态显示“减员审核中”。

### 减员审核通过

- `TeamMembership` → `removed`；
- 本赛事工作区权限回收；
- `CompetitionIdentity` 保留历史记录，但标记为 `revoked / removed`；
- 长期账号保持登录可用；
- 已形成且允许长期保留的个人资产按赛事规则保留；
- 其它赛事身份完全不受影响。

### 禁止

- 不注销 App 账号；
- 不解绑手机号；
- 不删除其它赛事身份；
- 不把用户退回“未注册”。

---

## 7. 手机号换绑

### 7.1 “赛事时间之外”的定义

不建议按平台全局赛事日历判断。

应按**当前用户自己的活跃赛事身份**判断：

```text
用户没有处于报名 / 审核 / 正赛中的 CompetitionIdentity
→ 允许自助换绑

用户存在活跃赛事身份
→ 暂停普通自助换绑
→ 如确有需要，进入人工高风险换绑
```

这样不会因为平台上“别的学校还有比赛”就永久锁死一个普通用户的手机号。

### 7.2 自助换绑流程

建议流程：

```text
已登录账号
→ 账号与安全
→ 更换手机号
→ 验证当前手机号
→ 输入并验证新手机号
→ 检查新手机号是否已属于其它 userId
→ 风险检查
→ 更新 loginIdentifier.phone
→ userId / Profile / CompetitionIdentity / LongTermAssets 全部保持原归属
→ 旧手机号与新手机号同时收到变更通知
→ 其它设备会话失效
→ 完成
```

### 7.3 新手机号已经绑定其它账号

**禁止自动合并。**

进入账号冲突流程：

- 提示该手机号已被其它账号使用；
- 保留当前账号现状；
- 允许进入人工核验；
- 任何证书、赛事身份、课程、简历资产都不由前端自动迁移。

### 7.4 原手机号无法接收验证码

提供“无法使用原手机号”人工恢复入口。

人工流程未来需要再确认可接受的身份核验材料，例如：

- 已绑定微信；
- 赛事实名信息；
- 学校 / 学号；
- 已验证邮箱；
- 人工客服审核。

施工阶段不自行决定最终 KYC 强度。

### 7.5 换绑频率

建议产品保留可配置冷却期，而不是代码写死。

例如：

```text
phone_binding_change_cooldown_days
```

具体 7 / 15 / 30 天由后续运营和风控确认。

## 8. PC 队长登录 / 注册设计

PC 报名门户的账号页应从“每个人都先注册三创赛独立账号”改为：

```text
队长进入 PC 报名门户
→ 手机号登录 / 注册
→ 命中核心学院长期账号则直接复用
→ 未注册则创建同一个长期账号
→ 队长填写团队和成员资料
→ 队员不再要求提前去 PC 单独注册
```

推荐首期支持：

- 手机号 + 验证码；
- 手机号 + 密码（已设置密码的用户）。

历史“登录名”如果仍需兼容，应作为迁移兼容入口，而不是继续成为新的主账号体系。

邮箱继续用于正式赛事通知，不作为第二套长期账号主键。

## 9. 状态矩阵

| 场景 | 系统动作 | 用户是否要重新注册 | 赛事身份 | App 使用 |
| --- | --- | --- | --- | --- |
| 未注册队员被队长提交 | 预开通长期账号 | 否，首次验证码认领 | 自动创建 | 可认领后使用 |
| 已注册队员，资料一致 | 复用原账号 | 否 | 自动新增 | 正常 |
| 手机号命中但资料冲突 | 暂停自动归并 | 否 | 暂不绑定 | 原账号正常 |
| 队员被减员 | 保留账号 | 否 | 本赛事 revoked/removed | 正常 |
| 用户参加另一场赛事 | 复用原账号 | 否 | identities[] 新增 | 正常 |
| 赛外换手机号 | 更新登录凭证 | 否 | 全部保留 | 正常 |
| 正处赛事周期申请换绑 | 普通自助阻止 | 否 | 不变 | 正常 |
| 新手机号已占用 | 冲突人工核验 | 否 | 不变 | 原账号正常 |

## 10. 本轮仍需 Owner 最终确认的少量规则

这些不妨碍当前原型继续施工，但真实后台实现前必须确认：

1. 自动开通的精确触发点，是“团队提交”还是“学校审核通过”；当前设计建议 **团队提交**。
2. 已有账号自动绑定的实名一致性校验字段最终采用哪些组合；当前设计建议至少手机号 + 姓名，并优先再比较学校 / 学号。
3. 活跃赛事期间是否完全禁止自助换绑，还是允许二次实名后换绑；当前设计建议普通自助禁止、人工通道保留。
4. 换绑手机号冷却期具体天数。
5. 原手机号失效时人工恢复所需的身份核验材料。
6. 同一学生在同一赛事是否允许跨团队 / 多赛道的特殊业务例外。

## 11. 施工优先级

### P0

1. PC 队员录入从“只能查找已注册邮箱”改为“直接录入成员 → 系统解析账号状态”；
2. 增加未注册自动开通 / 已注册自动绑定 / 冲突三态；
3. Mobile 首次登录支持“赛事自动开通账号认领”；
4. 已注册用户支持“新增赛事身份”通知态；
5. 减员不影响账号的状态表达。

### P1

6. `/me/accounts/phone` 手机号换绑原型；
7. 活跃赛事阻止自助换绑；
8. 新手机号冲突、原手机号不可用人工恢复入口；
9. 账号变更后的站内通知 / 安全通知表达。

### 验收底线

- 任何状态都不能创建第二份 session / identities / Profile 真相源；
- 手机号换绑后长期资产不迁移、不复制，只是同一 `userId` 的登录凭证变化；
- 赛事减员不能导致用户失去公共平台账号；
- 队长录错手机号不能无条件污染一个已有用户的赛事身份。
