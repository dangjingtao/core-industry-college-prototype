# 00｜产品总纲与业务上下文

> 状态：Current Baseline / 持续维护  
> 适用：优先用于手机端；PC 端可复用业务语义，但不得机械复制移动端交互。  
> 目的：把散落在旧 Mockplus、访谈、评审、重构线程和后续讨论中的高价值结论集中到一个可施工的产品上下文中。

---

## 1. 产品定位

本产品不是单一“三创赛 App”，也不是泛大学生生活平台。

更准确的定位是：

> **面向创新创业学生的长期平台。三创赛是第一批真实用户来源和当前最强业务入口，但平台需要继续承载其它赛事，并通过比赛机会、就业/实习机会、企业资源、课程、权益、可信成果和赛事 AI 陪跑形成长期价值。**

当前学生侧最核心的两个任务排序已经明确：

1. **参赛**；
2. **就业 / 实习。**

课程、权益、企业内容、资料、可信成果、AI 等都很重要，但它们原则上应增强这两条主线，而不是抢走首页和一级导航的主叙事。

“高粘度”比“每天高频点击”更符合业务目标。比赛、实习、长期资产等即使不是每天使用，也可能比一个高频但弱价值工具更重要。

---

## 2. 产品的时间轴

旧原型最大的结构问题不是功能太多，而是大量能力被平铺，没有清楚表达“什么时候发生、为什么发生、结束以后留下什么”。

本轮重构后应长期保持以下时间模型：

```text
公共平台长期存在
    ↓
发现赛事 / 机会
    ↓
某一场赛事开始形成上下文
    ↓
报名 → 学校审核 → 获得赛事身份
    ↓
赛事工作区 → 团队 / 项目 / 资料 / 权益 / 创赛工坊
    ↓
成绩 / 证书 / 项目成果
    ↓
赛事结束 / 权限回收
    ↓
经历 / 成绩 / 证书 / 学习成果进入长期账号
    ↓
继续参加其它赛事、找实习、整理简历
```

核心原则：

> **比赛会结束，账号和人的长期资产不会结束。**

---

## 3. 公共平台与赛事空间

普通学生即使没有任何参赛身份，也可以注册并长期使用 App。

### 公共平台层

至少承载：

- 赛事发现；
- 就业 / 实习 / 项目实践机会；
- 企业与品牌合作方；
- 公共课程；
- 通用权益；
- 公告 / 赛友内容 / 客服等支撑能力；
- 我的长期账号与资产。

### 赛事生命周期层

进入具体赛事后才出现：

- 报名 / 审核状态；
- 赛事身份；
- 当前团队与参赛项目；
- 赛事资料；
- 赛事专属权益；
- 赛事专属 AI，例如当前三创赛的“创赛工坊”；
- 成绩 / 证书 / 赛后出口。

不要把赛事专属能力重新放回全局工具箱，也不要让无赛事身份用户因为不能进赛事工作区而无法使用公共平台。

---

## 4. 账号、赛事身份、赛事上下文、长期资产

### 4.1 长期账号

App 学生账号是长期主体。

它承载：

- session / 登录状态；
- 个人资料；
- 多个赛事身份；
- 长期简历；
- 投递记录；
- 关注企业；
- 长期课程、权益、证书、成绩、经历等资产。

### 4.2 多赛事身份

一个账号可以同时关联多个赛事身份：

```text
User / App Account
  └─ CompetitionIdentity[]
       ├─ competitionId
       ├─ registrationStatus
       ├─ identityStatus
       ├─ validity / lifecycle
       └─ competition-scoped permissions
```

不能再退化成“一个账号只有一个当前赛事”的数据模型。

### 4.3 当前赛事上下文

“当前赛事”只代表用户此刻打开/进入哪一场赛事，不代表账号只拥有这一个身份。

深层页面必须保留 competitionId，避免从赛事 A 的 workspace / workshop 深页串到赛事 B。

### 4.4 参赛项目不是永久项目管理系统

参赛项目主要服务某一场赛事生命周期。

赛后长期保留的是：

- 参赛经历；
- 项目摘要；
- 团队角色；
- 比赛成绩；
- 证书 / 可信成果；
- 赛事关联课程与学习成果。

不默认把赛事项目做成比赛结束后还要长期运营的项目管理产品。

---

## 5. 五条母动线

任何页面、状态和后续功能调整都不能破坏以下五条母动线。

### A. 新用户公共平台

```text
注册/登录
→ 首页
→ 发现赛事 / 机会
→ 查看详情
→ 继续使用课程 / 权益 / 企业 / 个人资产
```

### B. 三创赛参赛

```text
赛事发现
→ 三创赛详情
→ 报名入口
→ 既有响应式报名层
→ 报名结果回流
→ 学校审核真实性
→ 获得赛事身份
→ 进入赛事上下文
```

### C. 赛事陪跑

```text
我的赛事
→ 当前赛事
→ 当前项目 / 当前状态
→ 创赛工坊
→ 下一步任务
→ answer / review / progress / result
→ 继续下一步
→ 最终成绩 / 证书
```

### D. 就业 / 实习

```text
首页 / 机会
→ 机会详情
→ 企业详情
→ 返回机会
→ 使用长期简历
→ 编辑 / 整理可信经历
→ returnTo 回原机会
→ 投递
→ applications / 状态回流
```

### E. 赛后长期资产

```text
赛事结束 / 权限回收
→ 赛后出口
→ 参赛经历 / 项目摘要 / 成绩 / 证书 / 课程成果
→ 我的长期资产
→ 简历表达
```

## 6. 报名系统边界

当前最急业务长期仍可能由三创赛报名牵引，但底层不能写死成三创赛专属。

已形成的方向：

- App 账号作为身份锚点；
- 复杂报名表单优先复用现有 PC 响应式报名层；
- App 负责进入报名、返回、报名状态、学校审核结果和赛事身份回流；
- 不同时维护两套互相冲突的完整报名表单。

旧 Mockplus 中队长/队员基础信息、答题、成员维护、承诺书等页面不能简单理解成“全部删除”：它们是旧业务证据。若后台/响应式报名层并未承接某项真实能力，需要重新恢复或明确替代方案。

---

## 7. 学校与老师

当前真实运营链路更接近：

```text
运营企业
→ 联系学校电商相关老师
→ 给老师开赛事范围内账号
→ 老师通过学生会 / 社团等渠道推动传播
→ 学生报名
→ 学校老师审核报名真实性
```

产品边界：

- 学校老师属于 Web / 运营后台角色，不进入学生 App；
- 权限应限制在“授权赛事 + 授权学校”范围；
- 现阶段不因为学校重要就建设学校独立门户、校园 SaaS、老师 App 工作台；
- 学生会 / 社团目前更像运营和传播渠道，不自动升级成独立平台角色。

---

## 8. 企业角色与商业闭环

企业在学生侧首先不是“招聘公司”。

更合理的心智是：

1. 赛事、权益、课程、活动、项目等资源的提供者；
2. 值得长期关注的品牌 / 合作方；
3. 实习与招聘是关系深化后的重要结果之一。

现阶段企业内容主要仍由运营方管理，不急于先做完整企业自运营后台。

### 企业为什么愿意投入

当前商业逻辑不是纯学生付费 C 端模式，更接近：

```text
企业投入赛事 / 权益 / 课程 / 活动 / 实习资源
→ 触达创新创业学生与项目
→ 持续运营、观察真实项目表现
→ 自然发现少量高潜学生 / 团队 / 项目
→ 产生实习、岗位、合作、项目连接
→ 沉淀案例与社会影响力
→ 吸引更多企业与资源方参与
```

目前企业最明确希望发现的高价值人才方向之一是营销 / 增长类人才；比赛成绩和真实项目表现是自然信号。

重要边界：

- 不建立对学生不透明的隐藏人才评分；
- 不把“抓到大鱼”做成必须稳定产出的产品 KPI；
- 学生是否接受企业后续机会，由学生自主选择；
- 产品应做的是把赛事成绩、项目经历、长期履历和后续机会自然连接起来。

---

## 9. 创赛工坊

“创赛工坊”目前首先是三创赛赛事 AI 陪跑能力，尤其聚焦美妆电商 / 新零售赛道。

它不是首期全平台通用 AI 助手。

首版不能依赖“平台一定知道学生精确比赛日”。真实情况可能只有官方时间窗口，学校、省份、赛道可在窗口内自行安排节点。

因此工坊应使用：

```text
官方时间窗口
+ 可选精确节点
+ 当前赛事身份
+ 当前项目状态
+ 用户/团队已填写材料
+ Task Runtime 进度
```

工坊首页最重要的问题始终是：

> **我现在最该做什么？**

S1–S6 不应再复制成六套页面系统，而应共享数据驱动 Task Runtime：

```text
skill / task config
→ answer
→ review
→ queued / running / failed / completed
→ result
→ next task
```

---

## 10. 课程

课程首期优先服务赛事，但必须按平台长期能力建设。

学生长期保存：

- 学习进度；
- 完课状态；
- 考试 / 测验结果；
- 证书；
- 其它学习成果。

赛事结束不能使课程学习记录消失。

旧原型还存在“学力值兑换课程”的经济模型；当前重构曾改为“权益/entitlement 解锁”。这两者不是同一个业务语义，是否保留旧积分兑换必须单独确认，详见缺口审计。

---

## 11. 权益

权益不是单一优惠券商城，但旧原型曾有较强“兑换中心 / 学力值”模式，因此需要区分“已确认的新结构”和“尚未确认是否废弃的旧经济模型”。

当前确定应支持的来源：

- 平台权益；
- 赛事专属权益；
- 企业权益；
- 活动权益。

关键状态：

- eligible / 可领取；
- ineligible / 无资格；
- claimed / 已领取待使用；
- used / redeemed / 已核销；
- expired / 已失效。

赛事权益资格必须读取共享 CompetitionIdentity，不应在权益模块另外复制一份赛事身份。

---

## 12. 长期资产、可信成果与简历

长期资产是把“赛事用户”变成“平台用户”的关键桥梁。

可信事实与学生表达必须分层：

### 系统事实

来源于：

- 赛事身份与结果；
- 参赛项目；
- 团队角色；
- 课程结果；
- 证书；
- 其它可信成果。

事实不应被简历编辑器直接改写。

### 学生自己的简历表达

学生可以决定：

- 哪些可信经历进入简历；
- 如何写个人优势；
- 如何描述教育经历与项目经验；
- 针对岗位如何组织表达。

当前需要继续确认旧原型中的结构化简历字段和 AI 润色 / AI 就业推荐是否仍属于有效产品范围。

---

## 13. 学生资料、问卷与画像

不要把“高级学生画像”当成已存在的成熟能力。

当前更现实的数据采集链：

1. 注册 / onboarding 收基础资料；
2. 报名获得较完整赛事信息；
3. 创赛工坊通过问卷继续获得项目阶段、需求、材料状态；
4. 已采集数据尽量进入统一字段体系，全平台复用；
5. 避免多个模块重复询问学校、专业、角色等相同信息。

旧 Mockplus 实际拥有比当前重构更完整的 onboarding 信息和 8 题问卷；这部分在页面合并时缩水，已列为高优先缺口。

---

## 14. 首页与一级导航

重构后的正确主叙事是：

### 一级

- 首页；
- 赛事；
- 机会；
- 我的。

### 首页第一层

- 值得参加的赛事；
- 就业 / 实习 / 项目机会。

### 第二层

- 我正在参加的赛事 / 当前赛事状态。

### 第三层支撑

- 课程；
- 权益；
- 企业资源；
- 可信成果；
- 资料；
- 内容和客服。

“课程很重要”“可信成果很重要”都不自动等于它们必须占底部一级导航。

---

## 15. 赛友内容与社区边界

旧一级导航“社区”实际混合了公告、企业和实训机会，会让用户误以为这里是论坛 / UGC 社区。

目前应按业务对象拆分：

- 公告 / 资讯；
- 企业；
- 实习 / 项目机会；
- 赛友风采。

“赛友风采”定位为精品内容模块，不做开放论坛；内容可以来自投稿与公众号精选，并清楚标注来源。

---

## 16. 线下运营 / 创域 / 扫码能力：历史讨论中的潜在方向

这部分来自后续产品讨论，属于**有价值的 Working Notes，不是已经冻结的正式 IA**。

曾讨论过把原“商城/福利”从单纯优惠券扩展为更有品牌感的“创域”，目标包含：

- 课程、打车、视频会员、外卖等现有权益；
- 更多贴近年轻人的线下活动；
- 企业 / 学校 / 社团共同参与运营；
- 扫码领取 / 核销 / 活动签到等线下触点；
- 本地化内容或权益；
- App 与小程序同构承接。

真正有潜力的产品链路不是“换一个商城名字”，而是：

```text
赛事 / 企业 / 学校组织线下活动
→ 学生现场扫码
→ 获取权益 / 记录参与关系
→ App 承接
→ 后续继续触达学生与项目
```

尚未明确：

- 运营权由平台集中还是下放学校 / 社团；
- 地区差异如何配置；
- 谁能发权益、谁能核销；
- 是否需要独立“创域”一级入口。

在真实运营规则没有确定前，不要为了“创域”名字重新扩张一级导航。

---

## 17. 状态与数据真相源：迁移时不可破坏

旧可交互重构最终形成过以下稳定边界，迁入新仓库时应继续保持语义：

### PublicPlatform / 长期账号公共状态

唯一维护：

- session；
- identities[]；
- applications；
- followedCompanies；
- 公共列表视图状态。

### WorkshopRuntime / 赛事局部 Runtime

唯一维护：

- competition lifecycle；
- workspace permission；
- taskRuns；
- workshop results；
- 当前赛事材料 / 局部 runtime。

它**不**拥有第二份 session 或 identities[]。

### LongTermAssets

维护：

- course learning records；
- benefits long-term records；
- certificates / results；
- profile；
- resume presentation。

它通过稳定 ID 引用赛事、企业、机会和工坊结果，不复制那些对象形成第二真相源。

### Support

维护通知、账号绑定、投稿、客服等支撑性原型状态。

### 禁止

- 第三套账号状态；
- 第二份赛事 lifecycle；
- 第二份 application store；
- 因查看历史资产重新激活赛事 workspace；
- 用 query 或局部组件状态偷偷覆盖长期账号事实。

## 18. 明确未决事项

### D03｜任务专区

旧原型存在：

- 空的全局“任务专区”；
- 日常任务；
- 核心任务；
- 企业任务；
- 与学力值奖励相关的任务。

但它们到底是平台任务、赛事任务、企业运营任务还是权益任务，关系未定义。

当前应继续冻结，不把创赛工坊 Task Runtime 误当全局任务中心。

### D08｜主体管理

旧原型存在：

- 学校 / 企业主体选择；
- 主体名称 / 标准代码 / 省市；
- 主体列表；
- 扫码绑定主体。

但“主体”与长期账号身份、学校、企业的真实关系未确认。

当前继续冻结，不用 UI 猜业务模型。

### 学力值经济模型

旧原型明确把学力值当成：

- 可收入 / 可消耗；
- 有余额和流水；
- 任务可赚取；
- 课程可用 200 学力值兑换；
- 兑换中心可按学力值排序。

旧重构后来把“学力值”改成了一个成长分数，并把课程解锁改为权益 entitlement。这是**业务语义替换**，不是简单重构。

是否彻底废弃积分经济模型，必须得到产品明确确认后再定。

---

## 19. 不可破坏的产品原则

- 不把平台重新写死成三创赛专属；
- 不把企业重新降成招聘公司目录；
- 不让课程 / 学力值 / 任务压过“参赛 + 就业”主轴；
- 不把学校老师塞进学生 App；
- 不构造对学生不透明的 AI 人才评分；
- 不同时维护两套完整报名系统；
- 不用页面数量当 KPI；
- 允许合并页面，但旧功能不能无理由缩水；
- 所有页面必须回答：从哪里来、当前上下文、主动作、下一步、返回、异常/无权限状态；
- 中保真优先结构、状态、动线和可维护性，不为装饰牺牲业务清晰度。
