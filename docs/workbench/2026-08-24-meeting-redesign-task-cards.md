# T028｜跨端登录 / 注册 / 账号绑定统一流程

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P0**  
**前置：T015、T015R1、F01、F03**

## 会议新增事实

会议同时明确了以下方向：

- 小程序首次微信登录后绑定手机号；
- 已注册 / 已参赛用户应被识别，可直接进入，不重复注册；
- PC 端也必须具备登录能力；
- PC 与手机端最终必须识别为同一个长期账号；
- 手机号被明确为更可靠的身份绑定凭证；
- 邮箱继续承担赛事正式通知，不应因此被误当成账号唯一锚点；
- 队长录入未注册队员后，存在“自动生成账号”的业务诉求。

## 需要确认

1. 长期账号的唯一身份锚点是否正式确定为手机号；
2. 微信 OpenID / UnionID 与手机号之间的绑定关系；
3. 已有三创赛账号与 App 账号如何识别、合并或认领；
4. 队长代录生成的“预账号”在队员首次登录时如何完成认领；
5. PC 登录是否采用手机号 + 密码 / 验证码，还是存在赛事历史账号兼容入口；
6. 邮箱仅作为通知字段，还是仍承担某些历史账号检索能力；
7. 手机号换绑允许的条件、频率和历史资产迁移规则。

## 重新设计范围

需要输出一张完整账号流：

```text
微信新用户
PC 新用户
三创赛历史用户
队长代录产生的未认领用户
        ↓
身份识别 / 账号命中
        ↓
手机号绑定或认领
        ↓
长期 App Account
        ↓
CompetitionIdentity[]
```

并覆盖：

- 首次登录；
- 老用户直接登录；
- 账号命中冲突；
- 手机号已被绑定；
- 队员认领预账号；
- 退出 / 重新登录；
- PC ↔ 手机数据一致。

## 约束

- 延续既有基线：App Account 长期存在，赛事身份按赛事生命周期存在；
- 不建立第二套 session / identities 真相源；
- 不因微信登录把长期账号写死为“小程序账号”；
- 不把邮箱与手机号各做一套互不相认的用户系统。

## 验收

- 输出账号状态图 + 新老用户跨端流程；
- 所有入口最终落到同一个长期账号；
- 队长代录用户具备明确认领路径；
- 原型可中保真模拟验证码 / 账号命中，不要求真实短信接口。

# T029｜三创赛报名端职责 + 团队建号 / 减员闭环

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P0**  
**前置：F00、T025、GAP-05**

## 会议口径存在冲突，必须先确认

本次纪要同时出现：

- “优先保障 PC 端体验，App 仅作辅助接入”；
- “整个报名流程迁移手机端”；
- “手机端通过 WebView 接 PC 报名流程”；
- “手机端是无电脑学生的兜底渠道，手机长表单体验不佳”。

这四条不能直接被施工线程自动合并成一个产品结论。

## 需要确认 A｜PC / 手机职责

Owner 需要明确最终模式：

- A：PC 响应式报名为主，手机 WebView / handoff 为兜底；
- B：手机成为主报名入口，但继续复用同一响应式报名层；
- C：未来另做原生手机报名，但本阶段仍沿用 F00。

在确认前，**不得拆掉 F00 既有“手机 → 响应式报名门户 → 状态回流”母动线。**

## 需要确认 B｜队长 / 队员账号

会议方向：

- 队长先注册、建立团队；
- 团队 ID 系统生成且只读；
- 队长可添加未注册队员；
- 队员不应失去独立账号；
- 手机号倾向作为身份绑定凭证；
- 邮箱主要承担正式通知。

待确认：

1. 队长添加哪些最小身份字段即可自动生成预账号；
2. 队员何时、通过什么方式完成账号认领；
3. 添加已注册用户与未注册用户是否同一入口；
4. 队员是否需要完成赛事规则答题，还是仅队长负责。

## 需要确认 C｜审核后减员

会议明确：审核后团队信息定型，只允许减员，不允许增员或替换。

但会议纪要中出现“需上传减员申请表”，而现有 `GAP-05` 的 2026-08-19 决策明确为：

- 赛事期减员不上传申请 / 证明材料；
- 选择成员 + 填写原因 + 提交审核即可。

这是**直接冲突**，必须由 Owner 决定哪一条覆盖哪一条，不能无痕改写历史。

同时确认：

- 减员申请表（若保留）的必填字段；
- 审核主体是校方老师、平台运营还是两级审核；
- 审核前成员事实不得直接变化。

## 重新设计范围

```text
队长创建团队
→ 添加已注册 / 未注册队员
→ 队员认领
→ 提交报名
→ 学校审核
→ 信息定型
→ 仅减员申请
→ 审核
→ 团队事实更新
```

## 验收

- PC / 手机职责有单一明确口径；
- 未注册队员不会成为“无主账号”；
- 审核通过后 UI 不再出现增员 / 替换入口；
- 减员材料规则与 GAP-05 冲突被显式解决并记录覆盖关系。

# T030｜承诺书体系收口

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P0**  
**前置：F00、PC02**

## 已确认方向

- 不做页面内电子签；
- 采用下载 → 打印 → 手写签字的线下签署方式；
- 指导老师承诺书入口文案应改为：**“下载指导老师承诺书模板”**；
- 老师承诺书基于学生课题信息生成 / 带出，不要求老师重新填写一套项目内容；
- 指导老师信息可以后置，不应卡死早期报名。

## 需要确认

1. 学生承诺书与指导老师承诺书是否最终都保留；
2. 两份模板具体内容差异；
3. 老师承诺书何时出现：添加指导老师后、审核后、还是项目提交后；
4. 签字后的文件是否需要系统上传，上传到哪里；
5. 会议中“Word 上传 / 下载”与“打印后附于作品后”的关系；
6. 老师端是否需要同步显示下载入口及签署状态。

## 重新设计范围

- 报名 / 项目材料页的承诺书卡片；
- 指导老师存在 / 不存在时的状态；
- 待生成 / 可下载 / 已下载 / 待签署 / 已提交（若需要上传）状态；
- 学生端与老师端的职责边界。

## 禁止

- 未确认前不要继续扩展电子签；
- 不要求老师重复录入已有项目字段；
- 不在两份承诺书是否保留尚未确认时做两套复杂页面。

## 验收

Owner 对“双承诺书是否保留 + 是否需要签后上传”给出明确结论后再做最终高保真收口。

# T031｜业绩报告 / 证书阶段状态与领取体验

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P1**  
**前置：F02、T008、PC04**

## 已确认方向

- “业绩报告”是学生**领取 / 下载结果**的入口，不是上传数据入口；
- 校赛、省赛、国赛等阶段的报告按赛事阶段出现；
- 晋级名单与证书签发必须分离；
- 普通电子证书与官方可信证书必须分开展示；
- 可信证书只在规定的高阶段 / 总决赛发放，不允许越级展示。

## 需要确认

1. 业绩报告右上角现有状态标识的语义与视觉形式（会议待办提到“是否为圆形工具”）；
2. 各阶段什么时候可领取报告；
3. 校赛 / 省赛 / 国赛 / 总决赛分别对应什么报告和什么证书；
4. 普通电子证书的实际签发阶段范围；
5. 可信证书签发平台 handoff 与“待签发 / 可领取 / 已领取 / 已撤销”等状态。

## 重新设计范围

建议统一为“赛事成果”阶段结构：

```text
当前阶段
→ 业绩报告
→ 晋级结果
→ 普通电子证书
→ 可信证书（满足资格时才出现）
```

但不得把报告、晋级、签证书合并成一个状态按钮。

## 验收

- 学生不会把“报告领取”误解成“数据上传”；
- 普通证书 / 可信证书视觉和业务层级明显区分；
- 不具备可信证书资格的用户看不到伪入口。

# T032｜教师审核工作台收口

**类型：重设计卡**  
**状态：可先施工结构，关键权限待确认**  
**优先级：P0**  
**前置：PC02、PC-BD01**

## 会议明确要求

教师端从泛后台收缩成纯审核工作台：

- 老师无需自主注册，由系统分配账号；
- 登录改为“账号 + 密码”，取消“选择姓名”式登录；
- 老师仅查看 / 处理本校学生团队；
- 删除跨校统计与跨校数据暴露；
- 当前 PC 教师端不扩展成综合运营后台；
- 学生端中混入的教师功能需要排查并移除。

## 需要确认

1. 教师账号具体由谁创建 / 分配；
2. 一个老师是否可能绑定多所学校或多个审核范围；
3. 审核动作的状态集合：通过 / 驳回 / 退回补充 / 仅查看；
4. 老师是否同时审核报名、减员、承诺书，还是不同事项由不同角色处理；
5. 学校下拉 / 学校归属数据是否完全信任学生报名字段，还是应由后台主数据校验。

## 重新设计范围

```text
教师账号密码登录
→ 本校审核工作台
→ 待审核团队
→ 团队基础信息 / 项目基础信息
→ 审核动作
→ 审核记录
```

## 禁止

- 不保留“选择姓名即可登录”；
- 不做跨校统计；
- 不把平台运营控制面能力复制给学校老师；
- 不把教师管理入口塞进学生 App。

## 验收

- 默认任何列表都只能看到授权学校 scope；
- 页面上不存在“跨校”残留；
- 未明确的后台运营能力继续留在 PC 管理端，不塞进教师工作台。

# T033｜应用中心互动体验 / 轻游戏重新定义

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P1**  
**前置：T018、T020、T021、T022、T026、F04 Decision A**

## 会议新增方向

- 应用中心继续保留 H5 基座能力；
- 可以接入轻量互动小游戏 / 养成类体验；
- 目标不是“工具宫格堆入口”，而是增加趣味性和用户粘性；
- 互动玩法可以成为学力值获取途径之一；
- 会议待办明确要求：重新设计互动体验板块**命名与玩法**。

## 需要确认

1. “应用中心”是否仍保留现名，互动板块使用什么名称；
2. 首个轻游戏具体是什么，不接受泛泛“养成类”占位；
3. 单次体验时长、每日重复频率、活动周期；
4. 是否纳入 D03 任务聚合；
5. 是否奖励学力值；若奖励，具体数值继续受 F04 Decision A 阻塞；
6. H5 游戏由平台自研、第三方接入还是运营配置；
7. 游戏结果是否沉淀为长期资产，默认不应自动变成“能力证明”。

## 重新设计范围

- 应用中心的信息架构；
- 互动板块命名；
- 游戏入口卡；
- 游戏详情 / 规则 / 奖励说明；
- 完成状态 / 奖励到账状态；
- 与首页高频入口的关系。

## 约束

- 不重复实现 T021 / T022 的另一套游戏宿主；
- 不绕过 F04 自行定义学力值数值；
- 不为了“活跃”把低价值小游戏提升为首页主叙事。

# T034｜课程考试 / 发证公信力规则收口

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P1**  
**前置：T011、T024、PC04**

## 会议新增方向

- 课程分为免费新手必修与付费兑换；
- 付费课程应有视频试看；
- 新手必修课存在明确授课周期 / 发证周期需求；
- 为避免证书泛滥，考试需要周期限制，会议举例为“每月两次”；
- 考完符合条件即可发电子证书，不与微专业课程强绑定。

## 需要确认

1. 新手必修课程的授课周期；
2. 新手课程何时发证；
3. 每门课程 / 每类考试每月允许几次；
4. 补考规则与冷却期；
5. 及格分数、证书签发条件、撤销条件；
6. 试看长度 / 试看章节；
7. 课程证书与赛事可信证书是否完全分层展示。

## 重新设计范围

- 课程详情试看入口；
- 学习进度；
- 考试次数 / 下次可考时间；
- 通过 / 未通过 / 冷却期；
- 证书领取与长期资产归档。

## 验收

- 用户能在考试前知道次数限制；
- 不通过隐藏规则突然阻止考试；
- 课程电子证书不与赛事“可信证书”视觉混同。

# T035｜兑换中心 / 卡券手机号绑定体验

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P1**  
**前置：T006、T019、F04 Decision A**

## 会议新增方向

- 权益不再直接跳转领取，先进入商品 / 权益详情页；
- 详情页明确内容、消耗与领取条件，确认后再扣取学力值；
- 线上卡券默认绑定当前登录手机号；
- 暂不开放频繁换绑，避免历史资产与领取漏洞。

## 需要确认

1. 学力值最终是可消费积分还是其他对象（继续依赖 F04 Decision A）；
2. 哪些权益必须绑定手机号，哪些无需手机号；
3. 手机号换绑后，未使用 / 已使用卡券如何处理；
4. 卡券是否允许转赠，会议当前方向倾向不允许；
5. 兑换失败 / 库存不足 / 资格不满足的状态；
6. 课程兑换与实物 / 卡券兑换是否共用同一详情结构。

## 重新设计范围

```text
权益列表
→ 权益详情
→ 资格 / 手机号 / 消耗确认
→ 确认兑换
→ 成功 / 失败
→ 卡券 / 课程 / 权益资产
```

## 约束

- 手机号继续复用 F01 `StudentProfile`；
- 不新建独立手机号 Store；
- 奖励 / 消耗金额未决前只做结构占位，不自行写死数值。

# T036｜地推邀请码 / 福利码落地修订

**类型：产品决策卡 + 重设计卡**  
**状态：待确认**  
**优先级：P1**  
**前置：T027、T015、T006**

## 与 T027 的关系

T027 已定义通用“邀请码 / 福利码”能力。本次会议新增了更具体的**地推人员固定邀请码**场景，不另造一套码系统，本卡只作为 T027 的业务修订。

## 会议新增方向

- 每个地推人员有固定专属邀请码；
- 学生扫码下载 / 注册后可领取指定权益；
- 需要据此核算拉新绩效；
- 地推码需要明确落地形式与权益绑定方式。

## 需要确认

1. 固定邀请码是文本码、二维码还是带参数链接；
2. 归因发生在下载、首次打开、注册还是完成手机号绑定；
3. 一个用户只能归因一个地推人员，还是允许覆盖；
4. 地推人员可绑定哪些权益；
5. 权益由谁配置；
6. 拉新绩效看注册数、激活数还是权益核销数；
7. 码的有效期、停用、人员离职后的处理；
8. 与普通新用户邀请码 / 活动福利码是否共用同一后台码池。

## 重新设计范围

```text
地推二维码 / 邀请码
→ 下载 / 打开 App
→ 登录 / 注册 / 绑定手机号
→ 邀请关系确认
→ 指定权益到账
→ 可查询领取结果
```

## 约束

- 不做多级分销；
- 不在前端自行判定邀请码有效；
- 归因和权益发放由稳定 ID / 后端规则表达，中保真原型可模拟 handoff。

# T037｜智能客服：知识库分流 + AI 工单兜底

**类型：重设计卡 / 修订卡**  
**状态：可施工中保真**  
**优先级：P1**  
**前置：T009、T009R1、GAP-10**

## 与旧卡关系

T009 / T009R1 已完成智能客服入口与浮窗形态。本次会议补的是客服**业务闭环**，不重做入口。

## 会议新增方向

- 基础问题先由知识库回答；
- 需要人工时，引导学生选择 / 输入赛道标签；
- 后台按赛道分配给对应人工客服；
- 非工作时间或客服繁忙时，由 AI 收集诉求生成工单；
- 人工后续处理并回复。

## 需要确认

1. 赛道标签是用户选择还是 AI 识别后让用户确认；
2. 人工客服渠道最终是站内工单、企业微信还是其它方式；
3. 工作时间 / 超时阈值；
4. 工单状态：待受理 / 已受理 / 待用户补充 / 已解决 / 已关闭；
5. 用户在哪里查看历史工单和回复；
6. AI 允许收集哪些字段，哪些敏感字段不得自动提取。

## 重新设计范围

```text
客服浮窗
→ 知识库回答
→ 仍未解决
→ 选择赛道 / 问题类型
→ 在线人工 或 AI 收集生成工单
→ 工单状态
→ 人工回复
→ 用户确认解决
```

## 约束

- AI 只做问题归纳 / 工单生成，不伪装成人工客服；
- 没有真实人工渠道时明确显示 handoff 状态，不伪造“客服已接入”；
- 不另建第二套通知系统，工单回复可复用通知中心。
