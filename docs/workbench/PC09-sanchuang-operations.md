# PC09｜三创赛运营工作台：视觉独立 + 营销实绩聚合

> 类型：施工卡 / 垂直赛事运营  
> 状态：PASS（2026-08-19 独立终审）  
> 优先级：P0  
> 分支：`dev`  
> 前置：PC02；建议与 PC08 数据骨架对齐后施工  
> 决策来源：2026-08-19 PC 原型接入需求讨论

---

## 1. 背景

三创赛当前不是普通“报名一次、出一个结果”的比赛。

学生参赛过程中会在第三方平台进行真实营销实践，例如：

- 抖音；
- 三创好物；
- 后续其它第三方平台。

这些平台会产生订单、直播、视频等营销数据。数据可通过第三方导出文件、API 或后续同步能力进入平台，并可能在未来成为比赛成绩依据之一。

因此三创赛需要从普通赛事的后台视觉和运营体验中**明确独立出来**；但独立的是运营工作台与视觉识别，不是底层赛事真相源。

---

## 2. 产品定位

推荐在 PC 一级导航增加：

```text
三创赛运营
```

与：

```text
赛事管理
```

并列。

两者关系：

```text
赛事管理 = 通用 Competition 基建
三创赛运营 = 基于同一 Competition 数据的垂直运营工作台
```

禁止复制第二套三创赛 Competition / Team / Registration 数据。

---

## 3. 路由与届次

推荐路由：

```text
/admin/sanchuang
/admin/sanchuang/:competitionId
/admin/sanchuang/:competitionId/performance
```

`/admin/sanchuang` 默认进入当前运营届次；页面必须允许明确切换届次 / Competition，而不是把“第十六届”写死成永远当前赛事。

三创赛 profile / capability mapping 应集中维护，禁止业务组件到处散落：

```text
isSanChuang === true
```

式特判。

## 4. 三创赛运营工作台

首页建议聚合：

```text
当前届次 / 生命周期 / 关键规模
报名团队
赛程阶段
营销实绩
排名 / 成绩
获奖结果
```

首版可以把已有能力做成摘要 + 下钻入口，不要求一次性重做所有模块。

推荐的信息结构：

```text
三创赛运营
├─ 赛事概览
├─ 报名团队
├─ 赛程
├─ 营销实绩
├─ 排名 / 成绩
└─ 获奖结果
```

其中本卡重点是“营销实绩”。

---

## 5. 视觉独立原则

三创赛运营允许有比普通赛事更强的品牌识别：

- 三创赛赛事标识；
- 当前届次明显可见；
- 独立的工作台 Hero / Header；
- 克制的赛事强调色；
- 核心数据更偏运营工作台表达。

但仍复用现有 PC Design Tokens、表格、筛选、卡片、状态组件与交互规范。

**视觉独立 ≠ 新建设计系统。**

评审人进入普通“赛事管理”和“三创赛运营”时，应明显感觉前者是平台通用控制面、后者是一个长期运营的旗舰赛事工作台。

---

## 6. 营销实绩聚合页

页面名称建议：

```text
营销实绩
```

它不把“直播数据 / 订单数据 / 视频数据”拆成三个一级后台菜单，而是在一个页面完成聚合。

### 6.1 顶部上下文

必须先明确当前统计对象：

- 当前赛事 / 届次；
- 团队；
- 赛项 / 赛道（适用时）；
- 当前阶段；
- 数据周期。

### 6.2 总览指标

根据当前 mock 数据可表达：

- GMV / 成交额；
- 订单量；
- 有效订单或退款后的净口径（若原型采用，必须写清口径）；
- 直播场次；
- 直播成交 / 观看等关键指标；
- 视频发布量；
- 视频播放 / 互动等关键指标。

不要求所有第三方平台指标完全一致；跨平台聚合只使用口径明确、可比较的数据。

### 6.3 渠道聚合

按来源平台展示：

```text
抖音
三创好物
其它平台
```

每个平台至少可查看：

- 数据周期；
- 最近导入 / 同步时间；
- 数据状态；
- 核心指标；
- 原始明细入口。

### 6.4 明细证据

同一聚合页下通过 tabs / sections 提供：

```text
订单明细
直播记录
视频记录
```

不再拆成三个一级菜单。

---

## 7. 导入、归集与导出

首版数据链路定义为：

```text
第三方导出文件 / API mock
→ 导入 / 同步批次
→ 平台归集
→ 聚合指标
→ 明细证据
→ 平台导出
```

原型至少需要表达：

- 数据来源平台；
- 导入 / 同步批次；
- 数据周期；
- 导入时间；
- 成功 / 失败 / 部分异常状态；
- 明细数量；
- 可导出当前筛选结果。

首版可以用稳定 mock 数据模拟导入，不要求真实接通抖音开放平台。

---

## 8. 未来作为成绩依据的证据链

由于营销实绩未来可能进入比赛评分，PC09 必须从第一版就保留可解释性：

```text
聚合指标
← 来源平台
← 导入 / 同步批次
← 原始订单 / 直播 / 视频记录
← 数据周期
```

管理员点击一个聚合值，应至少能够下钻到对应来源与明细范围。

需要明确区分：

- 原始第三方数据；
- 平台归集后的标准字段；
- 聚合展示结果；
- 未来评分结果。

**本卡不实现自动评分。**

可以预留“未来计入成绩”的数据接口 / 字段归属说明，但不得在没有评分规则的情况下擅自算分。

## 9. 与现有模块的关系

- Competition：继续复用 PC01 / PC02；
- Stage：与 PC08 CompetitionStage 对齐；
- Team：继续复用赛事团队；
- 报名资格：继续复用 PC02；
- 排名 / 获奖：首版复用当前已有展示或预留下钻，不在 PC09 重建评分规则；
- Audit Log：导入 / 人工修正等操作可以关联既有 Audit Log，不新建第二套审计系统；
- PC06 环境与日志：同步异常属于可观察性证据时可关联，但业务数据状态仍归 PC09 页面表达。

## 10. 最低交付

1. 一级导航出现独立“三创赛运营”；
2. 能明确识别当前三创赛届次并切换 / 选择 Competition；
3. 三创赛工作台视觉上明显区别于普通赛事管理，但继续复用 PC 设计系统；
4. 三创赛底层仍引用同一 Competition / Team / Registration；
5. 存在一个“营销实绩”聚合页；
6. 同页聚合订单、直播、视频三类数据；
7. 至少支持抖音、三创好物两个来源示例；
8. 支持团队 / 数据周期 / 来源筛选；
9. 展示导入 / 同步批次及状态；
10. 聚合指标可以追到原始明细范围；
11. 支持导出当前筛选结果的原型动作；
12. 页面明确标识“当前数据仅归集，不自动计入比赛评分”；
13. TypeScript / Vite build 通过；
14. focused browser assertions 至少覆盖：三创赛独立入口、届次上下文、营销实绩三类数据聚合、聚合 → 明细证据、普通赛事未出现三创赛专属运营入口。

---

## 11. 禁止

- 不把订单 / 直播 / 视频拆成三个一级菜单；
- 不复制第二套三创赛 Competition / Team / Registration；
- 不把三创赛硬编码成永远只有一个届次；
- 不在各组件散落 `isSanChuang` 特判；
- 不在没有规则时自动算比赛成绩；
- 不把聚合值做成无法追溯来源的“魔法数字”；
- 不为了视觉独立新建第二套设计系统；
- 不要求首版真实接通所有第三方平台。
