## 1. 目标

先建立 App 与 PC 运营端共用的核心大使计划业务模型，保证活动、团队、成员、点亮状态和推广成果只有一套业务真相源。

## 2. 施工范围

首版至少覆盖：

- 一期核心大使计划 Campaign；
- 活动覆盖学校及学校大使招募码；
- 核心大使团队；
- 核心大使 / 推广伙伴的活动成员关系；
- 团队招募码、个人专属推广来源；
- 有效新增记录；
- 简单团队激励处理状态。

固定规则：

1. 每个团队仅 1 位核心大使；
2. 同一期活动，一个用户只能属于一个推广团队；
3. 核心大使 + 至少 3 位推广伙伴，总人数达到 4 人后自动点亮；
4. 4 人只是门槛，不是团队人数上限；
5. 活动期间不可退队、不可换队；
6. 活动结束后团队关系结束，二维码失效，历史记录保留；
7. 核心大使计划属于运营活动，不复制赛事身份模型。

## 3. 不做

- 不做永久大使等级；
- 不做多级代理 / 子团队；
- 不做真实财务分账；
- 不在本卡锁定真实安装归因服务。

## 4. 验收

- [x] App 与 PC 可读取同一套活动 / 团队 / 推广成果状态；
- [x] 达到 4 人时团队自动点亮；
- [x] 点亮后继续加人不受 4 人限制；
- [x] 活动结束后二维码和团队关系失效，历史仍可读；
- [x] 未引入第二套 session / user / school / competition identity 真相源。

## 4.1 实现记录（2026-08-26）

- 共享模型位于 `packages/shared/src/campus-ambassador.ts`，导出活动、学校招募码、团队、成员、专属推广码、有效新增和激励状态类型。
- `@core/shared` 提供 `AmbassadorStateProvider` / `useAmbassadorState`；后续 T044 / T046 页面消费共享状态，不复制赛事身份或账号模型。
- 点亮规则由 `ambassadorTeamIsLit` / `deriveAmbassadorTeamStatus` 统一派生：恰好 1 位有效核心大使 + 至少 3 位有效推广伙伴，没有人数上限。
- 学校大使招募码与团队招募码分开维护；前者只关联活动 + 学校，后者在大使申请成功后按团队唯一生成，伙伴不会因同校共用学校码加入错误团队。
- 活动结束由 `ambassadorCampaignStatus` 派生为 `ended`；招募与加入操作在结束后拒绝，历史团队与有效新增记录保留。
- 有效新增使用 `campaignId + newAccountId` 幂等约束，避免同一活动重复计数。
