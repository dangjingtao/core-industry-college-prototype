# PC08｜赛事基础设施增强：赛事档案 + 阶段 + 报名记录 + 分类

> 类型：施工卡 / 赛事基建  
> 状态：待执行  
> 优先级：P0  
> 分支：`dev`  
> 前置：PC02 赛事控制台  
> 决策来源：2026-08-19 PC 原型接入需求讨论

---

## 1. 背景

当前核心产业学院对赛事产品边界的思路已经清楚，PC02 也已经建立统一 Competition 控制台；问题主要在于基础数据骨架仍偏薄。

旧系统虽然页面设计和数据组织较差，但暴露出几类值得吸收的赛事基础实体：

```text
Competition
├─ Category
├─ Stage / Round
└─ Registration projection
```

本卡是**基建升级，不是功能升级**：不复制旧赛事后台，不增加第二套赛事真相源，也不趁机引入新的比赛玩法。

---

## 2. 不可破坏的既有边界

PC02 已确认：

```text
外部权威赛事事实
≠ 平台承接报名流程
≠ 核心产业学院叠加服务
```

PC08 必须继续复用现有：

- PC01 `Competition` stable object；
- PC02 Competition 控制台；
- 现有 Team / TeamMember / CompetitionProject；
- registration portal 的报名事实；
- CompetitionIdentity / mobile `identities[]` 语义；
- 平台审核与官方资格双层状态。

**禁止新建第二份 Competition Store 或 Registration Store。**

---

## 3. 赛事基础档案增强

继续使用现有 Competition 对象与详情路由：

```text
/admin/competitions/objects/:competitionId
```

基础档案补齐可维护 / 可读字段关系，但不重复 PC01 已有 name / status / source / stable relation。

至少明确：

- 比赛名称；
- 比赛分类；
- 生命周期状态；
- 开始 / 结束时间；
- 来源与权威性；
- 展示状态；
- 基础资料 / 封面等当前原型确有消费位置的数据。

### 外部权威赛事

三创赛等外部权威赛事的官方字段继续遵守“API / 官方数据优先”。后台应表达来源 / 同步状态，不允许为了方便编辑而把外部权威事实改成纯人工真相源。

### 平台配置赛事

普通合作赛事继续允许由平台配置并维护。

---

## 4. CompetitionStage｜赛程 / 阶段

新增轻量赛事阶段实体：

```text
Competition 1 → N CompetitionStage
```

每个阶段至少包含：

- `stageId`；
- 阶段名称；
- 所属 `competitionId`；
- 开始时间；
- 结束时间；
- 比赛地点（可空）；
- 排序；
- 展示状态。

示例：

```text
报名与赛项选择
校园赛
省赛
全国现场总决赛
```

阶段状态首版优先由时间与赛事生命周期推导：

```text
未开始 / 进行中 / 已结束
```

不要同时再建设一套容易和时间冲突的复杂人工状态机。

PC08 只建立阶段骨架，不新增晋级算法、自动排位或淘汰规则。

---

## 5. CompetitionCategory｜比赛分类

新增轻量一级分类字典，至少包含：

- 分类名称；
- 排序值；
- 启用 / 停用；
- stable id / key。

示例可参考旧系统已有的创新创业、电子科技、企业赛事等概念，但最终示例应与当前核心产业学院已有赛事数据一致。

首版只做一级分类：

- 不做无限分类树；
- 不让分类承担报名规则；
- 不让分类变成另一套赛道 / track。

`Category` 与赛事内部 `Track / 赛道` 必须保持两个概念。

---

## 6. 报名记录统一视图

增加“比赛报名记录 / 参赛记录”管理视图，但它只是对现有报名事实的**统一投影**，不创建新的报名真相源。

列表至少可表达：

- 团队；
- 报名用户 / 队长；
- 关联学校 / Organization；
- 所属赛事；
- 平台审核状态；
- 官方资格状态（适用时）；
- 报名时间；
- 数据来源。

与旧系统不同：

- 当前业务没有赛事缴费逻辑，不引入“缴费状态”；
- 现有团队报名继续复用 Team / registration portal；
- 学校 / Organization 继续复用现有主体体系；
- 审核继续复用 PC02 双层资格模型，不再造“审核状态”。

允许从统一列表进入现有赛事 / 团队 / 报名详情，而不是复制详情页。

---

## 7. 页面组织建议

普通赛事仍以通用赛事控制台为主：

```text
赛事管理
→ 赛事列表
→ Competition 详情
   ├─ 基础资料
   ├─ 赛道
   ├─ 阶段 / 赛程
   ├─ 报名与资格
   ├─ 团队 / 项目
   ├─ 赛事资源
   └─ Workshop
```

分类管理可以作为赛事管理下的轻量配置页。

报名记录可作为赛事域的跨赛事查询页，也必须能按某一 Competition 下钻。

---

## 8. 最低交付

1. 现有 Competition 控制台继续是唯一赛事详情入口；
2. Competition 可关联一级 Category；
3. 存在可维护的比赛分类页，支持排序 / 启停；
4. Competition 可拥有多个 CompetitionStage；
5. 阶段支持名称、时间、地点、排序和可理解状态；
6. 至少一场三创赛存在 3 个以上阶段示例；
7. 至少一场普通合作赛事复用同一阶段模型；
8. 有统一报名记录视图，并复用现有 Team / registration / qualification 数据；
9. 报名视图不出现凭空新增的缴费逻辑；
10. 外部权威赛事仍能看到来源 / 官方同步边界；
11. TypeScript / Vite build 通过；
12. focused browser assertions 至少覆盖：阶段列表、分类与赛道边界、报名记录 → 现有详情下钻、普通赛事与三创赛复用同一底座。

---

## 9. 禁止

- 不复制旧系统“比赛管理”菜单数量；
- 不新建第二份 Competition 主数据；
- 不新建第二份 Registration 真相源；
- 不把 Category 与 Track 混淆；
- 不加入当前不存在的赛事缴费；
- 不让手工阶段状态与日期产生互相打架的真相；
- 不在本卡建设排名算法、自动评分、晋级规则或直播 / 视频 / 订单运营；
- 三创赛垂直运营能力由 PC09 承接。
