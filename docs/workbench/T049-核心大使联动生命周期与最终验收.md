## 1. 目标

在 T047、T048 完成 PC 配置和 App 扫码体验后，把 PC 与 App 串成一条可连续演示、状态一致、生命周期完整的核心大使业务链，并完成最终回归。

本卡不再扩展新的业务功能，只负责跨端真相源、生命周期、边界错误和最终验收。

## 2. 完整业务链

必须可现场连续演示：

```text
PC 创建活动 / 选择学校 / 配置申请表 / 绑定已发布条款
→ 生成学校招募二维码
→ 学生从 App 通用扫码器扫描学校码
→ 填写申请表 + 阅读并同意条款
→ 成为「核心大使 · 待点亮」
→ App 我的页出现灰色核心大使标识 + 我的团队
→ 核心大使展示团队招募二维码
→ 3 位推广伙伴扫码确认加入
→ 团队自动点亮
→ 大使 + 全部推广伙伴获得专属推广码
→ 团队继续邀请第 4 位及后续伙伴
→ 新成员立即获得专属推广码
→ 新用户通过个人推广码注册
→ 形成有效新增并归因到具体推广人员
→ 核心大使查看团队推广成果
→ 推广伙伴仍看不到成果数字
→ PC 查看活动 / 团队 / 成员 / 有效新增并处理团队激励
→ 活动结束
→ 招募与推广停止，历史保留
→ 后续新活动允许用户重新参加
```

## 3. App / PC 同一业务真相

中保真阶段不要求建设生产后端，但演示时 PC 与 App 必须观察到同一份核心大使业务状态。

至少保证：

- PC 创建 / 编辑的活动配置可被 App 消费；
- App 产生的大使、伙伴、点亮状态能在 PC 看到；
- App 产生的有效新增能在大使结果页和 PC 同步体现；
- PC 处理团队激励后状态可持续展示；
- 不允许通过两份互不相干的 seed / React 内存态假装“前后台已联动”。

可采用适合中保真的共享 demo store / mock persistence / 同源模拟方案，但不得因此引入生产级后端工程。

## 4. 活动生命周期

### 活动开始

- 现阶段维持“按 startsAt / endsAt 自动判断未开始、进行中、已结束”的规则；
- 是否增加手动发布 / 开始动作属于独立产品决策，不在本卡擅自增加；
- 未开始活动的学校招募码不可形成有效申请。

### 活动结束

到期后必须按有效状态收口，而不是只改页面标签：

- 团队逻辑状态视为已结束；
- 学校招募码失效；
- 团队招募码失效；
- 专属推广码失效；
- 不再产生新有效新增；
- 已存在成员、团队、推广成果、申请信息、激励状态作为历史保留；
- 结束后的旧团队不得阻止同一账号参加后续新活动。

## 5. 已知边界问题收口

### A｜过期推广码页面卡死

活动结束后访问个人推广码，不应继续展示可提交注册表单再静默失败。

要求：

- 页面进入时根据活动有效状态判断；
- 已过期显示明确“活动已结束 / 推广码已失效”；
- 不产生 pending 按钮永久禁用状态。

### B｜同活动其他团队成员模拟为“新用户”

共享动作已阻止同一期活动既有成员被计为新用户，但页面当前反馈可能卡死。

要求：

- 页面与共享动作对“已注册 / 已绑定本期团队 / 已计入”的结果有一致可读反馈；
- 被拒绝时恢复可操作状态；
- 不重复计有效新增。

### C｜历史团队阻塞未来活动

- “同一用户同一期只能属于一个团队”只在 campaign 范围内生效；
- 已结束活动的历史成员身份不得阻止未来 campaign 的大使申请或伙伴加入。

### D｜非本人 / 未登录团队信息暴露

- 团队成员列表、团队招募码和成果页必须继续遵守身份权限；
- 未登录或非本团队成员不得通过直输路由看到私有团队信息；
- 推广伙伴只看团队/活动状态和自己的个人推广码，不看任何成果数字及其他成员明细。

### E｜未开始 / 已结束码的用户反馈

- 学校码、团队码、推广码在未开始 / 已结束场景都要给明确结果；
- 不进入错误表单后才提示“无效”；
- 不出现无返回路径的死页面。

## 6. PC 最终检查

- 活动列表数据与活动详情一致；
- 团队点亮、成员数、有效新增、激励状态使用同一业务事实；
- 团队详情可看到核心大使申请信息；
- 运营只向核心大使处理一次团队激励，不建设伙伴分账；
- 历史活动 / 团队仍可查看，不与当前活动数据混淆。

- [ ] 大使 / 伙伴权限隔离正确；

- [ ] 活动结束后学校码、团队码、个人推广码均不可继续形成新业务；
- [ ] 历史数据保留且下一期可重新参加；
