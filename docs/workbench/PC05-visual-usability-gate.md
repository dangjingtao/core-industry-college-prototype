# PC05｜PC 视觉与可用性硬验收门槛

> 状态：PC05 必须执行  
> 性质：**硬验收，不是视觉润色，不是可选优化**  
> 适用范围：`/admin/*` 整体，包括 PC01–PC04 已落地页面与 PC05 新增页面。

## 目标

PC 管理端最终交付对象是运营、审核人员和管理者，不是参与建模的开发者。

最终标准：

> **第一次打开后台的人，不需要理解我们的数据模型、stable ID、Runtime、truth source 等工程背景，也能知道自己在哪里、能做什么、下一步应该点哪里。**

如果页面虽然数据契约正确，但呈现为字段堆叠、架构说明板、调试面板或“施工现场”，则 PC05 不得 PASS。

---

## A. 页面任务可理解性｜P0

每个主要页面必须在首屏回答：

1. 我现在在哪个业务模块？
2. 这个页面主要处理什么业务？
3. 当前最重要的状态是什么？
4. 我现在能做的主要动作是什么？
5. 完成后下一步去哪里？

不得要求运营先理解 `CompetitionIdentity / DataSource / Runtime / stable relation` 才能操作。

工程信息可以保留，但必须退到次级信息层。

---

## B. 信息层级｜P0

页面优先级统一为：

```text
业务标题 / 当前上下文
→ 关键状态 / 风险
→ 主操作
→ 核心业务内容
→ 次级关系与历史
→ stable ID / provenance / App consumer / debug 信息
```

禁止：

- stable ID、数据来源、App consumer、truth boundary 抢占首屏主体；
- 一页同时展开所有关系、所有解释、所有字段；
- 用大段说明文代替页面结构；
- 把“架构正确”当成“运营可用”。

---

## C. 导航与命名｜P0

- 全局导航必须稳定、统一，不允许 PC01–PC04 各自再造 Shell；
- 导航和页面标题优先使用业务语言；
- 英文模型名只在必要的辅助信息中出现；
- 当前所在域、对象、详情 / 编辑层级必须一眼可辨；
- 返回路径必须明确，不依赖浏览器后退猜测。

例如：

- 首屏应写“学生赛事身份”“官方资格”“权益履约”等业务概念；
- 不应把 `Runtime Record / Relation / Truth Boundary` 当作主要操作文案。

---

## D. 列表 / 详情 / 编辑 Pattern｜P0

### 列表

运营首先看到：

- 对象是谁；
- 当前状态；
- 关键业务归属；
- 是否存在异常 / 待处理；
- 可执行的主要动作。

不要默认把所有 stable ID、来源、保留策略、App consumer 全塞进主表格。

### 详情

详情页必须形成清楚的主次：

```text
核心业务事实
→ 当前状态和操作
→ 关联资源 / 主体
→ 历史 / 审计
→ 技术元数据
```

### 编辑

- 主操作必须明确；
- 必填、只读、危险字段视觉区分；
- 保存后影响范围表达清楚；
- 保存成功后重新进入页面必须仍然存在，不接受“提示成功但数据没写回”的假保存。

---

## E. 状态与视觉语义｜P0

同类状态必须使用稳定的文案、颜色和组件语义：

- 正常 / 已完成；
- 待处理 / 等待；
- 风险 / 异常；
- 已关闭 / 已撤销 / 无效；
- 只读 / Runtime 事实。

禁止为了“好看”让不同业务状态共用误导性色彩，也禁止满屏彩色 Tag 导致状态失焦。

---

## F. 高风险操作｜P0

以下操作必须和普通编辑形成明显视觉区别：

- 学生账号冻结 / 解冻；
- 官方资格人工修正；
- 批量 CompetitionIdentity 修改；
- 批量证书签发 / 撤销；
- 权限提升。

要求：

- 明确风险说明；
- 明确对象与影响范围；
- 明确审批状态；
- 不与普通“保存”按钮并排伪装成同等级操作。

---

## G. 数据架构信息的正确位置｜P0

PC01 固定下来的这些信息仍然必须保留：

- stable ID；
- 五类 provenance；
- Role / Module Permission / Data Scope；
- App consumer；
- 生命周期保留策略；
- 跨域 stable relation。

但它们在最终 UI 中主要承担 **追溯、诊断、治理** 角色，不应持续主导普通运营工作流。

建议落点：

- 详情页“数据与关系”次级区；
- 抽屉 / 展开区；
- 审计 / 数据来源模块；
- 必要时的只读元数据行。

**不得为了视觉简化删除这些契约，也不得为了契约完整把它们全部铺在首屏。**

---

## H. 独立可用性复审｜PC05 PASS 前必须执行

PC05 不只做代码 / 数据契约复审，还必须进行一次独立视觉与操作复审。

复审者以“第一次使用后台的普通运营人员”视角，不先阅读实现代码，至少走：

1. 总览 → 找到一个赛事 → 判断当前资格 / 待处理事项；
2. 赛事 → Organization → 返回赛事；
3. 机会列表 → 详情 → 编辑 → 保存 → 返回详情；
4. 课程 → 完成规则 / 证书规则；
5. 权益 → 判断资格与履约方式；
6. 学生 → CompetitionIdentity → 长期资产；
7. 高风险动作 → 审批 / Audit Log。

每条动线必须回答：

- 是否知道自己在哪里；
- 是否知道下一步点哪里；
- 是否能区分查看、普通编辑和高风险动作；
- 是否出现工程字段压过业务信息；
- 是否出现“不知道这个字段是干什么的”的密集施工现场感。

出现明显迷失、信息噪声或操作不确定，即使数据契约全部正确，也判 `CHANGES REQUIRED`。

---

## I. PC05 最终双门禁

```text
Gate A｜产品 / 数据 / 权限 / 跨端契约 PASS
+
Gate B｜视觉层级 / 操作可理解性 / 普通运营可用性 PASS
=
PC05 PASS
```

任何一个 Gate 未通过，PC05 都不得 PASS。

视觉评审不是要求做营销站或追求装饰性，而是把当前正确的数据控制面真正收成一个**人能工作的后台**。
