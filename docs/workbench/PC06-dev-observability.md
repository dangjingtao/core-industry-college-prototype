# PC06｜开发环境观察台 + 日志与告警

> 优先级：P0  
> 分支：`dev`  
> 前置：PC01 控制面底座；可与 PC05 并行

---

## 1. 背景

会议确认，PC 后台需要补充面向开发人员的环境观察能力。

当前诉求不是建设完整 APM / Grafana 替代品，也不是把原始日志直接铺到页面，而是让开发人员打开页面后，能在很短时间内判断：

> **当前开发 / 测试环境是否健康；异常大致发生在哪一层；下一步应该去看哪类日志。**

同时会议要求：

- 环境状态明确区分开发环境与测试环境；
- 开发人员可以一眼看到常见运行指标；
- 环境警告需要从原始日志中提炼，形成可理解的异常 / 告警；
- 日志需要按类型组织，而不是把所有内容混成一份 raw log；
- 具体操作记录必须清晰可追溯，但不得重复建设第二套 Audit Log。

### 与老板数据大屏的边界

老板大屏是独立的业务数据展示能力，面向汇报 / 投屏，主要展示业务规模、增长、分布、趋势和结果。

**PC06 不负责老板大屏，也不得把以下内容塞进老板大屏：**

- 服务器指标；
- 环境状态；
- 开发日志；
- 异常告警；
- 原始请求 / 系统日志。

## 2. 产品定位

新增一个后台开发观察模块，建议路由：

```text
/admin/observability
```

中文导航名称建议：

```text
环境与日志
```

它仍属于 `/admin/*` PC 控制面，不另造独立系统，也不成为新的业务真相源。

页面第一目标不是“信息最多”，而是：

```text
10 秒内知道环境是否正常
→ 30 秒内定位异常大类
→ 需要时再进入日志证据
```

---

## 3. 第一层：环境总览

顶部必须提供明确的环境切换：

```text
开发环境 | 测试环境
```

首期只实现会议已明确的开发 / 测试环境，不自行扩展生产环境。

环境总览至少展示：

- 当前环境；
- 综合健康状态；
- 当前版本 / build 标识；
- 最近部署时间；
- 最近一次健康检测时间；
- 运行时长或等价可理解状态（若当前原型数据可表达）。

综合状态建议保持简单：

```text
正常 / 有警告 / 异常
```

不得仅依赖颜色表达。

---

## 4. 第二层：常见开发指标

开发打开页面后必须能直接看到常见指标，不要求先进入日志。

### 4.1 服务健康

至少覆盖当前原型可表达的主要依赖：

- Web / 前端；
- API；
- 数据库；
- 对象存储；
- 关键第三方接口 / 数据源。

每项至少提供：

- 状态；
- 最近检测；
- 延迟或可用性指标（若有）；
- 最近异常摘要。

原型阶段可以使用结构化 mock，但字段语义要能映射未来真实健康检查接口。

### 4.2 请求指标

优先展示常见、开发可快速判断的指标：

- 请求量 / 请求速率；
- 请求成功率；
- 4xx；
- 5xx；
- 平均响应时间；
- P95 响应时间。

不要求首版实现复杂 percentile / trace 分析。

### 4.3 资源指标

当当前环境能够提供或可合理模拟时展示：

- CPU；
- 内存；
- 磁盘；
- 连接数 / 等价资源占用指标。

首版重点是“是否接近风险状态”，不是做专业资源监控平台。

### 4.4 任务 / 数据同步

至少可看到：

- 最近一次同步时间；
- 成功 / 失败数量；
- 当前失败任务；
- 队列积压或待处理数（若有）；
- 最近一次外部数据源异常。

需要与 PC 后台既有 API 同步、文件导入、批处理等数据来源语义保持一致。

---

## 5. 第三层：异常与告警

### 5.1 原则

主界面展示的是**人能读懂的异常结论**，不是 raw log。

示例：

```text
测试环境 · 三创赛数据同步失败 · 已持续 12 分钟
```

而不是直接把：

```text
connection timeout after 10000ms
```

作为唯一提示。

### 5.2 告警信息至少包含

- 环境；
- 严重级别；
- 发生对象 / 服务；
- 简短可理解标题；
- 首次发生时间；
- 最近发生时间；
- 当前状态：未恢复 / 已恢复；
- 关联日志入口。

### 5.3 异常摘要

环境首页至少给出：

- 最近 1 小时异常数；
- 最近 24 小时异常数；
- 当前未恢复告警数；
- 最近异常列表。

不要在首版建设复杂告警策略编排器。

---

## 6. 日志分类

日志模块至少区分以下三类：

### A. 系统日志

服务运行、请求失败、依赖异常等系统事件。

### B. 数据同步 / 导入日志

包括：

- API 同步；
- 文件导入；
- 批处理；
- 外部数据源同步；
- 冲突 / 失败记录。

### C. 告警日志

由系统事件或数据异常提炼出的、真正需要人员关注的告警记录。

告警日志不是复制一份系统日志，而是对原始事件的可处理化表达。

### 操作日志不在这里另造

“谁在什么时候对什么对象做了什么”属于既有：

```text
权限与审计 / Audit Log
```

PC06 可以提供关联入口或摘要，但**禁止再造第二套操作审计真相源**。

---

## 7. 最近变更 / 部署

环境页需要能快速回答“是不是刚有人改过东西”。

至少展示近期：

- 部署时间；
- 版本 / build 标识；
- 执行人；
- 环境；
- 部署结果；
- 与异常发生时间的基本关联线索。

原型阶段允许使用 mock 记录，不要求接入完整 CI/CD 平台，但字段边界需要真实可替换。

```text
环境与日志

[开发环境] [测试环境]

```

视觉上继续遵守现有 PC 中保真后台，不为“科技感”另起一套设计系统。

## 9. 数据与原型边界

首期是中保真原型，可以使用结构化 mock 数据，但必须满足：

1. mock 以未来真实 API / health check / metrics / logs 的字段归属为依据；
2. 不把 mock 写成“永远真实”的静态业务事实；
3. 开发 / 测试环境必须真正使用不同的 mock 数据集合，能表现不同健康状态；
4. 告警必须能追到对应日志记录；
5. 已恢复异常与未恢复异常要能区分；
6. 页面刷新不应随机改变状态，保证评审可复现。

首版**不要求**：

- 接入 Prometheus；
- 接入 Grafana；
- 接入 OpenTelemetry 全链路；
- 建设日志采集后端；
- 自研完整 APM；
- 实时 WebSocket 指标流；
- 告警规则可视化编排。

## 11. 最低交付

1. `/admin/observability` 可进入；
2. 后台导航存在明确“环境与日志”入口；
3. 开发 / 测试环境可以切换；
4. 首屏具备环境总览 + 服务健康 + 请求指标 + 常见资源指标；
5. 有任务 / 数据同步状态；
6. 有最近 1h / 24h 异常与未恢复告警摘要；
7. 系统日志、同步 / 导入日志、告警日志可分类查看；
8. 告警可打开对应日志证据；
9. 最近部署 / 变更可查看；
10. 操作审计不重复建设，只提供到既有权限与审计的关联出口；
11. 页面具备至少一组“测试环境存在异常、开发环境正常”的可复现演示数据；
12. TypeScript / Vite build 通过；
13. 补至少一条 focused browser assertion，验证环境切换与告警 → 日志动线。
