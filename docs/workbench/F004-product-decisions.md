> 决策日期：2026-08-17  
> 基线分支：`dev`  
> 决策卡来源：`docs/workbench/00-work-ledger.md` F04  
> 约束：本文件只冻结业务语义、真相源边界与后续施工方向；**不直接恢复 `/tasks`、`/me/subjects`、旧兑换中心或任何一级导航。**

## 0. 决策原则

F004 的目的不是“把旧 Mockplus 全部恢复”，而是解决旧功能与当前产品骨架之间的语义冲突。

本轮继续遵守以下已确认基线：

1. 产品主轴仍是 **参赛 + 就业 / 实习**；
2. App Account 是学生长期主体，CompetitionIdentity 按赛事存在且可并存；
3. 创赛工坊属于具体赛事上下文，不是全局 AI / 全局任务中心；
4. 企业是赛事、权益、课程、活动、机会的资源与品牌主体，不只是一张招聘公司卡；
5. 学校老师属于 Web / 运营后台角色，不进入学生 App；
6. 不新增第二份 session / identities / lifecycle / applications 真相源；
7. 不构造对学生不可解释的隐藏人才评分。

因此，F004 的统一判断标准是：

> **旧能力有真实业务价值就保留语义，但必须放回正确的领域对象；旧页面名称和旧 IA 不作为恢复依据。**

# Decision A｜学力值

## 决策

**学力值恢复为“可收入、可消费、有余额、有流水”的平台积分对象。**

不再把“基础账号 + 学习 + 投递”计算出来的单一成长总分继续称为“学力值”。

也就是说，本轮选择原 F04 的 **A：保留积分经济**，而不是把积分与成长评分混在一起。

### 1. 学力值的业务语义

学力值是平台内的非现金积分：

- 有当前余额；
- 有收入 / 消耗流水；
- 可以由任务、活动、学习等明确规则发放；
- 可以按具体资源配置用于兑换课程、权益、活动名额或其它可兑换资源；
- 不等同于人民币，不表达提现、转账或现金价值。

建议后续领域对象表达为：

```text
LearningPointAccount
  ├─ balance
  └─ transactions[]
       ├─ earn / spend
       ├─ amount
       ├─ sourceType
       ├─ sourceId
       └─ createdAt
```

名称可以在施工卡中再按代码风格调整，但业务语义已经冻结。

### 2. “成长分”怎么办

当前重构中把基础账号、学习、投递累计成 GrowthScore 的做法，**不再作为正式产品模型继续扩大**。

如果未来确实需要成长表达，应优先使用：

- 可解释的成就；
- 已完成课程；
- 可信成绩 / 证书；
- 项目经历；
- 明确维度的能力证据。

当前阶段不再额外建立一个“成长总分”，避免与学力值再次发生语义冲突。

### 3. 旧兑换中心怎么办

**不恢复成独立“积分商城”主叙事。**

旧兑换中心的有效能力拆回到当前“权益 / 活动 / 课程”资源模型中：

```text
资源本身
+ 获取方式
  ├─ 免费领取
  ├─ 身份资格领取
  ├─ 学力值兑换
  ├─ 完成任务获得
  └─ 活动 / 扫码获得
```

“兑换”是资源的一种获取方式，不再单独定义一套与权益系统平行的商品世界。

未来“创域”可以承接这些资源的品牌化发现与本地运营，但不能因此复制一份新的兑换真相源。

### 4. 课程是否还能使用学力值兑换

**可以，但按课程 / 权益配置，不是所有课程统一如此。**

课程的获取方式允许并存：

- 免费；
- 赛事 / 企业 / 活动 entitlement 解锁；
- 学力值兑换；
- 其它明确授权方式。

已有长期学习记录仍属于 LongTermAssets；支付 / 解锁方式不能复制一份课程学习状态。

### 5. 任务奖励是什么

任务奖励不是固定等于学力值。

统一允许：

```text
Reward
  ├─ learningPoints
  ├─ entitlement / benefit
  ├─ achievement
  └─ none
```

一个任务可以无奖励，也可以由业务配置一种或多种明确奖励。

**禁止为了让学力值“有用”而反向制造低价值任务。**

# Decision B｜第三方账号

## 决策

**两类能力都存在，但必须拆开命名和建模。**

### A. 登录 / 联系方式绑定

当前已有的：

- 邮箱；
- 微信；
- 企业微信；

属于账号安全、登录、联系方式或客服触达能力。

建议统一语义：

```text
AccountBinding / ContactBinding
```

它们继续属于账号 / Support 范畴。

### B. 业务渠道账号

旧原型中的：

- 抖音达人；
- 快团团；
- 三创好物；
- 平台账号 ID；
- 昵称；
- 正常 / 停用 / 注销状态；

不是登录绑定，而是学生参与电商、内容、赛事实践时使用的 **业务渠道账号**。

该能力保留，但不把 2026 年旧原型中的平台列表硬编码成永久枚举。

建议领域语义：

```text
BusinessChannelAccount
  ├─ channelType
  ├─ accountId
  ├─ nickname
  ├─ status
  ├─ verificationStatus
  └─ source / scope
```

### 使用边界

- 不是所有学生注册时必填；
- 只有具体赛事、项目、企业任务或工坊步骤确实需要时才采集 / 选择；
- 可作为长期账号资产复用，避免同一抖音 / 快团团账号每场赛事重复填写；
- 具体支持的平台由业务配置，不由前端写死；
- 自报账号与平台 / 运营已验证账号必须区分验证状态。

因此，旧页面名“第三方账号”不恢复；后续应分别落在“账号绑定”和“业务渠道账号”两个明确入口。

# Decision C｜D03 任务体系

## 决策

**恢复“任务”产品能力，但 `/tasks` 只做聚合视图，不成为第五套任务真相源。**

旧原型中的日常任务、核心任务、企业任务有真实业务证据，因此不废弃；但必须按作用域归属。

## 1. 任务分层

### 平台成长任务

作用域：长期公共平台。

适合：

- 完善资料；
- 首次学习；
- 参与明确的平台活动；
- 有实际价值的长期成长动作。

不恢复“为了刷活跃而刷活跃”的任务设计。

### 赛事任务

作用域：某个 `competitionId`。

适合：

- 赛事要求；
- 赛事阶段行动；
- 非 AI 的报名后 / 赛中待办；
- 赛事运营动作。

赛事结束后不能继续以“当前任务”身份存在，但完成记录可以进入赛事经历。

### 企业任务

发行主体可以是企业，但必须有明确 scope：

- 平台活动；
- 某场赛事；
- 某个企业合作项目；
- 某次创域活动。

企业任务不是企业可以任意向所有学生广播任务。现阶段内容与发布权限仍由平台 / 运营控制或审核。

### 权益任务

**不单独建立第四种任务引擎。**

“完成任务后获得权益”属于 Reward / Eligibility 规则：

```text
Task completion
→ reward / entitlement
```

权益系统读取任务完成事实，不复制任务进度。

### 创赛工坊 Task Runtime

继续保持现有边界：

```text
skill / task config
→ answer
→ review
→ queued / running / failed / completed
→ result
→ next task
```

它是赛事 AI 陪跑 Runtime，不并入通用任务 Store。

通用任务中心如果需要展示“创赛工坊下一步”，只能展示一个带 `competitionId + runtimeTaskRef` 的引用卡片，点击后回到创赛工坊；任务中心不得拥有第二份工坊进度。

## 2. `/tasks` 的产品定位

未来 `/tasks` 可以解冻，但定位为：

> **“我现在可执行的跨域待办 / 任务聚合页”。**

它聚合：

- 平台任务；
- 当前有效赛事任务；
- 企业 / 活动任务；
- 指向创赛工坊下一步的引用。

每条任务必须显示：

- 来源；
- 所属赛事 / 企业 / 活动；
- 截止或有效期；
- 完成条件；
- 奖励；
- 去完成的目标页面。

### 真相源原则

```text
/tasks = read model / aggregator
```

而不是：

```text
/tasks = 所有领域任务的总 Store
```

这样可以避免与 WorkshopRuntime、赛事状态、权益状态再次产生重复事实。

# Decision D｜D08 主体管理

## 决策

旧原型里的“主体”实际应拆成：

1. **平台登记的组织实体**；
2. **用户与组织之间的关联 / 认证关系**。

学生 App 不再承担“创建学校 / 企业主体”的职责。

## 1. 主体到底是什么

后续统一按组织实体理解，建议语义：

```text
Organization
  ├─ school
  └─ company
```

学校和企业本身由平台 / 运营后台登记、导入或审核，不由学生输入名称和标准代码后直接创建一份新主体。

## 2. 用户与主体的关系

学生账号与学校 / 企业之间建立的是：

```text
OrganizationAffiliation
  ├─ accountId
  ├─ organizationId
  ├─ role / relationType
  ├─ scope
  ├─ status
  ├─ source
  └─ verifiedAt
```

例如：

- 学生属于某学校；
- 某赛事报名验证了学校关系；
- 某人通过邀请加入企业项目；
- 某次活动建立了临时组织参与关系。

这与 CompetitionIdentity 不是同一个对象，不能互相替代。

## 3. 谁创建、谁审核、谁绑定

- Organization：平台 / 运营创建或导入；
- 学校老师 / 企业管理员的管理权限：Web / 后台认证与授权；
- 学生：只能申请、接受邀请或被业务流程自动建立 affiliation；
- affiliation 是否可信，由报名、后台审核、邀请或其它明确来源决定。

## 4. 扫码绑定的真实语义

二维码不再表达“扫一下创建 / 认领主体”。

它只能用于一个明确的关系动作，例如：

```text
扫码
→ 识别 organization / campaign / invitation
→ 用户确认
→ 建立 pending / verified affiliation 或活动参与关系
```

扫码必须带上下文，不能存在一个无业务来源的“万能主体二维码”。

## 5. `/me/subjects` 怎么办

**旧 `/me/subjects` 不按原页面恢复。**

后续如果学生侧确实需要查看组织关系，应改成更直白的“我的学校 / 组织关联”能力，优先挂在 Profile / Account，而不是建立一个抽象的“主体管理中心”。

因此：

- D08 的业务模型已解冻；
- 当前 `/me/subjects` 仍保持 blocked，直到有独立施工卡按新语义改造；
- 不允许施工线程拿“已决策”当理由原样恢复旧主体 UI。

# Decision E｜创域 / 本地运营 / 扫码

## 决策

**“创域”确认作为平台后续可持续运营的品牌化业务面，但当前不是一级导航。**

它不是简单把“商城”改名，而是承接：

- 权益；
- 青年线下活动；
- 企业 / 学校合作活动；
- 本地化资源；
- 扫码领取 / 核销 / 签到；
- 线上线下参与关系沉淀。

## 1. 当前 IA

底部一级导航继续保持：

- 首页；
- 赛事；
- 机会；
- 我的。

创域首期应作为首页 / 权益 / 活动体系中的二级品牌入口与运营聚合面，不抢“参赛 + 就业 / 实习”的主叙事。

后续是否升级一级入口，以真实使用量、运营供给和复访价值决定，不在 F004 预设。

## 2. 谁能组织

现阶段采用 **平台治理 + 有限下放**：

- 平台 / 运营方：拥有最终发布、上下架、核销规则与风险控制权；
- 企业：可以作为 sponsor / organizer 提供权益、活动和资源，但首期仍由平台 / 运营代管或审核发布；
- 学校 / 社团：可以成为活动协办方、校园触点和执行方；权限按具体活动 / 学校范围授予，不建设完整校园 SaaS；
- 不因为“社团能办活动”就给社团全平台运营权限。

这与当前“学校老师走 Web / 运营后台、企业暂不建设完整自运营后台”的基线一致。

## 3. 本地化如何做

每个创域资源 / 活动都应有明确 scope：

```text
global
province
city
school / campus
competition
campaign
```

用户看到什么，优先根据：

- StudentProfile 中已知学校 / 城市；
- 当前主动选择的地区；
- 当前赛事上下文；
- 明确 eligibility。

首期不依赖精确 GPS，也不要求开启定位才能使用。

## 4. 扫码能力统一成“动作入口”

扫码不是一个独立业务中心，而是统一能力，根据 QR 上下文执行：

- 领取权益；
- 核销权益；
- 活动签到；
- 接受组织 / 活动邀请；
- 打开指定活动 / 资源详情。

扫码结果必须落回原领域事实：

```text
Benefit entitlement / redemption
Activity participation / check-in
Organization affiliation
```

禁止再造一个“扫码记录 Store”代替这些领域对象。

## 5. 线上线下关系怎么沉淀

只沉淀可解释的行为事实，例如：

- 报名；
- 到场 / 签到；
- 权益领取；
- 核销；
- 完成活动任务；
- 关注企业 / 后续申请机会。

这些事实可以用于用户自己查看经历、活动后续触达和明确规则的推荐，但**不能暗中折算成一个人才分或用户价值分。**

# Decision F｜AI 简历 / 人才能力表达

## 决策

采用“**AI 可辅助表达，可信事实必须可追溯，人才判断不做黑盒总分**”的原则。

### 1. AI 简历润色

**可以恢复，优先级 P2。**

但只作用于学生可编辑的 resume presentation，例如：

- 个人优势；
- 项目描述；
- 在校经历；
- 针对岗位的表达组织。

AI 不得直接改写系统可信事实：

- 比赛成绩；
- 证书；
- 团队角色；
- 课程结果；
- 已验证学校 / 身份。

交互上必须由用户主动触发，并允许对比 / 接受，而不是静默覆盖。

### 2. AI 就业推荐

**可以作为未来“机会匹配建议”，但不恢复成 AI 就业总分。**

只有在岗位要求、StudentProfile、长期简历、可信成果等数据来源足够明确时才施工。

推荐理由必须能回答：

- 哪些岗位要求匹配；
- 使用了哪些用户已知资料；
- 哪些只是模型建议；
- 用户如何修改偏好或资料影响结果。

### 3. 核心能力雷达

**当前阶段不恢复旧雷达图。**

只有未来每个能力维度都有：

- 明确定义；
- 可追溯证据；
- 更新规则；
- 面向学生的解释；

才允许重新设计。

不能根据“参加过比赛 / 学过课 / 投过简历”随意拼一个能力百分比。

### 4. 企业侧人才发现

企业可看到或被匹配到的信号，应来自：

- 真实比赛成绩；
- 项目经历；
- 课程 / 证书 / 可信成果；
- 学生主动填写的简历；
- 学生明确允许进入机会匹配的资料。

不建立隐藏的“人才总分”“高潜指数”作为核心决策依据。

# 9. 后续施工边界

F004 完成后可以拆新的施工卡，但任何施工卡必须遵守：

1. 不在 F004 分支直接新增页面 / Store / 路由；
2. 学力值账户不得与课程学习状态、权益状态重复；
3. `/tasks` 只能聚合，不复制 WorkshopRuntime；
4. Organization 不能由学生端随手新建；
5. QR 的结果必须写回所属领域；
