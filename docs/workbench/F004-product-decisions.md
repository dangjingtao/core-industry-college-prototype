## 0. 文档定位与决策原则

F004 的目的不是“把旧 Mockplus 全部恢复”，而是解决旧功能与当前产品骨架之间的语义冲突，并为产品责任人提供一份可逐项确认的推荐方案。

本轮继续遵守以下已确认基线：

1. 产品主轴仍是 **参赛 + 就业 / 实习**；
2. App Account 是学生长期主体，CompetitionIdentity 按赛事存在且可并存；
3. 创赛工坊属于具体赛事上下文，不是全局 AI / 全局任务中心；
4. 企业是赛事、权益、课程、活动、机会的资源与品牌主体，不只是一张招聘公司卡；
5. 学校老师属于 Web / 运营后台角色，不进入学生 App；
6. 不新增第二份 session / identities / lifecycle / applications 真相源；
7. 不构造对学生不可解释的隐藏人才评分。

因此，F004 的统一判断标准是：

> **旧能力有真实业务价值可以提出保留方案，但必须放回正确的领域对象；旧页面名称和旧 IA 不作为恢复依据；方案合理也不能替代产品确认。**

### 状态定义

本文件只使用以下三类决策状态：

- **Confirmed**：已经由产品责任人明确认可，或属于已有正式产品基线，可直接作为施工 Guardrail；
- **Recommended / Pending Confirmation**：方案可以保留并继续讨论，但不能据此开工或修改正式业务语义；
- **Deferred**：当前明确不进入施工范围，未来满足条件后再重新评估。

# Decision A｜学力值

## 状态

**Recommended / Pending Confirmation**

### Confirmed Guardrail

**“学力值积分”与 GrowthScore / 成长评分必须是两个不同语义，不能继续混用同一个名字或同一状态模型。**

是否恢复积分经济、GrowthScore 是否继续存在，以及兑换范围，仍待产品责任人确认。

## 推荐方案（业务选择待确认）

**推荐：学力值恢复为“可收入、可消费、有余额、有流水”的平台积分对象。**

如果采用该方案，不再把“基础账号 + 学习 + 投递”计算出来的单一成长总分继续称为“学力值”。

也就是说，本方案推荐原 F04 的 **A：保留积分经济**，但当前不把这一选择写成已确认事实。

### 1. 学力值的推荐业务语义

若产品确认恢复积分经济，学力值建议作为平台内的非现金积分：

- 有当前余额；
- 有收入 / 消耗流水；
- 可以由任务、活动、学习等明确规则发放；
- 可以按具体资源配置用于兑换课程、权益、活动名额或其它可兑换资源；
- 不等同于人民币，不表达提现、转账或现金价值。

建议后续领域对象表达为：

```text
LearningPointAccount
  ├─ balance
  └─ transactions[]
       ├─ earn / spend
       ├─ amount
       ├─ sourceType
       ├─ sourceId
       └─ createdAt
```

名称可以在后续施工卡中再按代码风格调整；**该对象目前是推荐模型，不是已冻结真相源。**

### 2. “成长分”怎么办

已确认的是：**GrowthScore 不能继续占用“学力值”这个积分语义。**

尚未确认的是 GrowthScore 本身最终如何处理：

- 废弃；
- 改名后作为独立成长表达保留；
- 不做总分，改成成就 / 证据维度；
- 其它产品方案。

本推荐稿倾向于：如果未来确实需要成长表达，应优先使用：

- 可解释的成就；
- 已完成课程；
- 可信成绩 / 证书；
- 项目经历；
- 明确维度的能力证据。

但“当前阶段不再额外建立成长总分”仍属于产品选择，未确认前不能由施工线程擅自删除或扩展现有 GrowthScore。

### 3. 旧兑换中心怎么办

**推荐：不恢复成独立“积分商城”主叙事。**

如果产品确认恢复积分经济，旧兑换中心的有效能力建议拆回当前“权益 / 活动 / 课程”资源模型中：

```text
资源本身
+ 获取方式
  ├─ 免费领取
  ├─ 身份资格领取
  ├─ 学力值兑换
  ├─ 完成任务获得
  └─ 活动 / 扫码获得
```

“兑换”作为资源的一种获取方式，不再单独定义一套与权益系统平行的商品世界。

未来“创域”如果确认落地，可以承接这些资源的品牌化发现与本地运营，但不能因此复制一份新的兑换真相源。

### 4. 课程是否还能使用学力值兑换

**推荐：可以按课程 / 权益配置，而不是所有课程统一如此。**

如果产品确认这一经济模型，课程的获取方式可以并存：

- 免费；
- 赛事 / 企业 / 活动 entitlement 解锁；
- 学力值兑换；
- 其它明确授权方式。

已有长期学习记录仍属于 LongTermAssets；支付 / 解锁方式不能复制一份课程学习状态。

### 5. 任务奖励是什么

**推荐：任务奖励不固定等于学力值。**

若任务体系与积分经济都被确认，建议统一允许：

```text
Reward
  ├─ learningPoints
  ├─ entitlement / benefit
  ├─ achievement
  └─ none
```

一个任务可以无奖励，也可以由业务配置一种或多种明确奖励。

无论最终是否恢复积分经济，都继续守住：**禁止为了让学力值“有用”而反向制造低价值任务。**

# Decision B｜第三方账号

## 状态

**Recommended / Pending Confirmation**

### Confirmed Guardrail

登录 / 联系方式绑定与业务渠道账号是两个不同对象；如果两类能力都存在，必须拆开命名和建模。

尚未确认旧抖音达人 / 快团团 / 三创好物等业务渠道账号在当前产品中是否仍有效。

## 推荐方案（业务选择待确认）

### A. 登录 / 联系方式绑定

当前已有的：

- 邮箱；
- 微信；
- 企业微信；

属于账号安全、登录、联系方式或客服触达能力。

建议统一语义：

```text
AccountBinding / ContactBinding
```

它们继续属于账号 / Support 范畴。

### B. 业务渠道账号

旧原型中的：

- 抖音达人；
- 快团团；
- 三创好物；
- 平台账号 ID；
- 昵称；
- 正常 / 停用 / 注销状态；

不是登录绑定，而是学生参与电商、内容、赛事实践时使用的 **业务渠道账号**。

如果产品确认这类业务今天仍需要，建议保留为独立对象，但不把 2026 年旧原型中的平台列表硬编码成永久枚举。

建议领域语义：

```text
BusinessChannelAccount
  ├─ channelType
  ├─ accountId
  ├─ nickname
  ├─ status
  ├─ verificationStatus
  └─ source / scope
```

### 使用边界建议

如果业务渠道账号被确认保留，建议：

- 不是所有学生注册时必填；
- 只有具体赛事、项目、企业任务或工坊步骤确实需要时才采集 / 选择；
- 如果属于长期账号资产，可复用并避免同一抖音 / 快团团账号每场赛事重复填写；
- 如果只属于特定赛事 / 项目，则应 scoped，不强行长期化；
- 具体支持的平台由业务配置，不由前端写死；
- 自报账号与平台 / 运营已验证账号必须区分验证状态。

因此，旧页面名“第三方账号”不建议恢复；但“业务渠道账号是否恢复”仍等待产品确认。

# Decision C｜D03 任务体系

## 状态

**Recommended / Pending Confirmation**

### Confirmed Guardrail

- 创赛工坊 Task Runtime 继续保持赛事 scoped；
- 如果未来存在 `/tasks`，它只能做跨域 read model / aggregator；
- `/tasks` 不得拥有第二份 WorkshopRuntime 任务进度。

尚未确认的是：是否真的恢复平台长期任务、企业任务，以及是否需要独立 `/tasks` 入口。

## 推荐方案（业务选择待确认）

如果产品确认恢复通用“任务”能力，建议按作用域归属，而不是恢复一个无边界的总任务 Store。

旧原型中的日常任务、核心任务、企业任务有真实业务证据，因此可以作为候选需求；但旧页面存在不等于新产品必须恢复。

## 1. 任务分层建议

### 平台成长任务

候选作用域：长期公共平台。

适合：

- 完善资料；
- 首次学习；
- 参与明确的平台活动；
- 有实际价值的长期成长动作。

不建议恢复“为了刷活跃而刷活跃”的任务设计。

是否需要平台长期任务本身，仍待产品确认。

### 赛事任务

候选作用域：某个 `competitionId`。

适合：

- 赛事要求；
- 赛事阶段行动；
- 非 AI 的报名后 / 赛中待办；
- 赛事运营动作。

如果采用，赛事结束后不能继续以“当前任务”身份存在，但完成记录可以进入赛事经历。

### 企业任务

如果产品确认企业任务仍是当前能力，发行主体可以是企业，但必须有明确 scope，例如：

- 平台活动；
- 某场赛事；
- 某个企业合作项目；
- 某次创域活动。

不建议默认赋予企业向所有学生广播任务的权限。现阶段内容与发布权限仍应服从平台 / 运营现有治理基线。

企业任务本身是否恢复，仍待产品确认。

### 权益任务

**架构建议：不单独建立第四种任务引擎。**

如果出现“完成任务后获得权益”，建议视为 Reward / Eligibility 规则：

```text
Task completion
→ reward / entitlement
```

权益系统读取任务完成事实，不复制任务进度。

### 创赛工坊 Task Runtime

继续保持现有已确认边界：

```text
skill / task config
→ answer
→ review
→ queued / running / failed / completed
→ result
→ next task
```

它是赛事 AI 陪跑 Runtime，不并入通用任务 Store。

如果未来任务中心需要展示“创赛工坊下一步”，只能展示一个带 `competitionId + runtimeTaskRef` 的引用卡片，点击后回到创赛工坊；任务中心不得拥有第二份工坊进度。

## 2. `/tasks` 的推荐产品定位

如果产品确认确实需要独立 `/tasks`，推荐定位为：

> **“我现在可执行的跨域待办 / 任务聚合页”。**

候选聚合内容：

- 平台任务；
- 当前有效赛事任务；
- 企业 / 活动任务；
- 指向创赛工坊下一步的引用。

每条任务建议显示：

- 来源；
- 所属赛事 / 企业 / 活动；
- 截止或有效期；
- 完成条件；
- 奖励；
- 去完成的目标页面。

### 真相源原则（Confirmed）

```text
/tasks = read model / aggregator
```

而不是：

```text
/tasks = 所有领域任务的总 Store
```

这样可以避免与 WorkshopRuntime、赛事状态、权益状态再次产生重复事实。

**在产品确认是否恢复任务产品能力前，`/tasks` 继续 blocked。**

# Decision D｜D08 主体管理

## 状态

**Recommended / Pending Confirmation**

### Confirmed Guardrails

- `Organization` 与 `OrganizationAffiliation` 分离；
- 学校 / 企业不应由学生输入名称和标准代码后直接创建；
- CompetitionIdentity 与 OrganizationAffiliation 不是同一对象；
- 不恢复一个无业务来源的“万能主体二维码”；
- 学校老师继续属于 Web / 运营后台角色。

尚未确认的是：学生侧到底是否需要查看 / 管理组织关系，以及 `/me/subjects` 最终去向。

## 推荐方案

旧原型里的“主体”建议拆成：

1. **平台登记的组织实体**；
2. **用户与组织之间的关联 / 认证关系**。

学生 App 不承担“创建学校 / 企业主体”的职责，这一 Guardrail 已确认；但学生侧是否需要显式组织关系能力仍待产品确认。

## 1. 主体到底是什么

建议后续统一按组织实体理解：

```text
Organization
  ├─ school
  └─ company
```

学校和企业本身由平台 / 运营后台登记、导入或审核，不由学生输入名称和标准代码后直接创建一份新主体。

## 2. 用户与主体的关系

若产品确认需要组织关系能力，建议学生账号与学校 / 企业之间建立：

```text
OrganizationAffiliation
  ├─ accountId
  ├─ organizationId
  ├─ role / relationType
  ├─ scope
  ├─ status
  ├─ source
  └─ verifiedAt
```

候选场景包括：

- 学生属于某学校；
- 某赛事报名验证了学校关系；
- 某人通过邀请加入企业项目；
- 某次活动建立了临时组织参与关系。

其中哪些关系需要成为长期 affiliation 仍要按真实业务确认，不能因为模型能表达就全部长期化。

这与 CompetitionIdentity 不是同一个对象，不能互相替代。

## 3. 谁创建、谁审核、谁绑定

推荐规则：

- Organization：平台 / 运营创建或导入；
- 学校老师 / 企业管理员的管理权限：Web / 后台认证与授权；
- 学生：只能申请、接受邀请或被业务流程自动建立 affiliation；
- affiliation 是否可信，由报名、后台审核、邀请或其它明确来源决定。

其中企业项目关系是否进入长期 affiliation，仍待产品确认。

## 4. 扫码绑定的真实语义

二维码不应表达“扫一下创建 / 认领主体”。

如果未来有组织关系扫码，建议只能用于一个明确的关系动作，例如：

```text
扫码
→ 识别 organization / campaign / invitation
→ 用户确认
→ 建立 pending / verified affiliation 或活动参与关系
```

已确认的 Guardrail 是：扫码必须有业务上下文，不能存在一个无业务来源的“万能主体二维码”。

## 5. `/me/subjects` 怎么办

**当前继续 blocked。**

推荐方向是：如果学生侧确实需要查看组织关系，应改成更直白的“我的学校 / 组织关联”能力，优先挂在 Profile / Account，而不是建立一个抽象的“主体管理中心”。

但最终需要产品确认：

- 是否需要学生侧入口；
- 删除旧 `/me/subjects`；
- 改名；
- 或换成其它业务入口。

因此当前状态是：

- D08 的架构 Guardrail 已确认；
- D08 的学生侧产品范围仍未解冻；
- `/me/subjects` 继续 blocked；
- 不允许施工线程拿本文件原样恢复旧主体 UI。

# Decision E｜创域 / 本地运营 / 扫码

## 状态

**Recommended / Pending Confirmation**

### 已形成共识 / Confirmed Guardrails

- “创域”不是把旧商城简单改名；
- 方向可以覆盖权益、青年活动、本地运营和线上线下连接；
- 当前不升级为一级导航，不抢“首页 / 赛事 / 机会 / 我的”四个一级入口；
- QR 是领域动作入口，最终事实必须落回 Benefit / Activity / Affiliation 等所属领域，而不是形成独立扫码真相源。

仍需确认：创域是否正式作为二级运营品牌、治理权如何分配、地域 scope、学校 / 社团权限、发行 / 核销权限和首期扫码动作范围。

## 推荐方案（业务选择待确认）

推荐把“创域”作为平台后续可持续运营的品牌化业务面候选，而不是单纯商城：

- 权益；
- 青年线下活动；
- 企业 / 学校合作活动；
- 本地化资源；
- 扫码领取 / 核销 / 签到；
- 线上线下参与关系沉淀。

这些内容是推荐范围，不代表首期必须全部建设。

## 1. 当前 IA

已确认：底部一级导航继续保持：

- 首页；
- 赛事；
- 机会；
- 我的。

推荐：如果创域确认落地，首期作为首页 / 权益 / 活动体系中的二级品牌入口与运营聚合面，不抢“参赛 + 就业 / 实习”的主叙事。

后续是否升级一级入口，以真实使用量、运营供给和复访价值决定，不在 F004 预设。

## 2. 谁能组织

以下是**推荐治理模型，尚未确认**：

> 平台治理 + 有限下放

候选职责：

- 平台 / 运营方：拥有最终发布、上下架、核销规则与风险控制权；
- 企业：可以作为 sponsor / organizer 提供权益、活动和资源，但首期由平台 / 运营代管或审核发布；
- 学校 / 社团：可以成为活动协办方、校园触点和执行方；权限按具体活动 / 学校范围授予，不建设完整校园 SaaS；
- 不因为“社团能办活动”就给社团全平台运营权限。

这套方案与当前“学校老师走 Web / 运营后台、企业暂不建设完整自运营后台”的基线兼容，但**兼容不等于已确认**。

产品 / 运营仍需明确：

- 企业能否自主发布；
- 学校 / 社团能做什么；
- 谁能发行权益；
- 谁能核销；
- 审核责任在哪里。

## 3. 本地化如何做

推荐每个创域资源 / 活动有明确 scope，但具体层级尚未确认。

候选 scope：

```text
global
province
city
school / campus
competition
campaign
```

用户看到什么，可以优先参考：

- StudentProfile 中已知学校 / 城市；
- 当前主动选择的地区；
- 当前赛事上下文；
- 明确 eligibility。

首期是否需要全部六层 scope 仍待产品确认。

当前不建议依赖精确 GPS，也不要求开启定位才能使用；如果未来业务确实需要位置权限，应另做独立决策。

## 4. 扫码能力统一成“动作入口”

Confirmed Guardrail：扫码不是一个独立业务中心；扫码结果必须写回所属领域事实。

候选动作包括：

- 领取权益；
- 核销权益；
- 活动签到；
- 接受组织 / 活动邀请；
- 打开指定活动 / 资源详情。

**首期到底支持哪几个动作仍待产品 / 运营确认。**

无论首期选择哪些动作，都必须满足：

```text
Benefit entitlement / redemption
Activity participation / check-in
Organization affiliation
```

等领域对象拥有最终事实，禁止再造一个“扫码记录 Store”代替这些领域对象。

## 5. 线上线下关系怎么沉淀

推荐只沉淀可解释的行为事实，例如：

- 报名；
- 到场 / 签到；
- 权益领取；
- 核销；
- 完成活动任务；
- 关注企业 / 后续申请机会。

这些事实可以用于用户自己查看经历、活动后续触达和明确规则的推荐，但已确认的边界是：**不能暗中折算成一个人才分或用户价值分。**

# Decision F｜AI 简历 / 人才能力表达

## 状态

**Recommended / Pending Confirmation**

### Confirmed Guardrails

- AI 不得直接改写比赛成绩、证书、团队角色、课程结果、已验证学校 / 身份等系统可信事实；
- AI 生成内容必须与可信事实层分离；
- 不构造黑盒“人才总分 / 高潜指数”；
- 核心能力雷达在缺少可追溯证据模型时 **Deferred**；
- 如果未来提供 AI 辅助编辑，应由用户主动触发并确认，而不是静默覆盖。

尚未确认：AI 简历润色和可解释机会匹配是否正式进入后续产品范围，以及优先级。

## 推荐原则

采用“**AI 可辅助表达，可信事实必须可追溯，人才判断不做黑盒总分**”的原则。

其中 Guardrail 已确认；具体 AI 功能是否建设仍待产品确认。

### 1. AI 简历润色

**Recommended / Pending Confirmation。**

如果产品确认进入后续范围，建议只作用于学生可编辑的 resume presentation，例如：

- 个人优势；
- 项目描述；
- 在校经历；
- 针对岗位的表达组织。

AI 不得直接改写系统可信事实：

- 比赛成绩；
- 证书；
- 团队角色；
- 课程结果；
- 已验证学校 / 身份。

交互上必须由用户主动触发，并允许对比 / 接受，而不是静默覆盖。

当前**不能因为本推荐稿存在就把 AI 简历润色排入施工卡**。

### 2. AI 就业推荐 / 机会匹配

**Recommended / Pending Confirmation。**

如果未来产品确认需要，推荐做“机会匹配建议”，而不是 AI 就业总分。

只有在岗位要求、StudentProfile、长期简历、可信成果等数据来源足够明确时才适合施工。

推荐理由必须能回答：

- 哪些岗位要求匹配；
- 使用了哪些用户已知资料；
- 哪些只是模型建议；
- 用户如何修改偏好或资料影响结果。

是否进入当前产品范围仍待确认。

### 3. 核心能力雷达

**Deferred。**

当前阶段不恢复旧雷达图。

只有未来每个能力维度都有：

- 明确定义；
- 可追溯证据；
- 更新规则；
- 面向学生的解释；

才允许重新设计。

不能根据“参加过比赛 / 学过课 / 投过简历”随意拼一个能力百分比。

### 4. 企业侧人才发现

Confirmed Guardrail：企业侧不能依赖隐藏的人才总分作为核心决策依据。

如果未来产品确认建设机会匹配，企业可看到或用于匹配的信号应优先来自：

- 真实比赛成绩；
- 项目经历；
- 课程 / 证书 / 可信成果；
- 学生主动填写的简历；
- 学生明确允许进入机会匹配的资料。

不建立隐藏的“人才总分”“高潜指数”作为核心决策依据。
